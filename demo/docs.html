Introduction

cracked-up is a JavaScript library for making sound and music in the browser by writing code. You describe a sound as a chain of simple parts, such as an oscillator into a filter into a volume control, and a musical clock plays your patterns in time. It is meant for live coding, and for apps that let people write small music scripts. 

__().saw({ id: 'bass', gate: 'closed' }).lowpass(700).gain(0.3).to('main');

__.transport.sequence('bass', { steps: [55, 0, 55, 82.4], step: '1/8' }, (ev) => {
  if (ev.value) __('#bass').set({ frequency: ev.value }).trigger({ duration: 0.15 });
});

Every example on this page has a Try it link that opens it in the live demo, where you can change it while it plays.

Where it comes from

cracked-up is based on I Dropped My Phone The Screen Cracked by Bill Orcutt, called Cracked for short on this page. Cracked had the idea this library keeps: one object, __, with which you chain audio nodes together and later find them again with selectors like the ones in CSS, such as __('#bass') or __('lowpass').

cracked-up is a rewrite, not a new version of Cracked. It was written from scratch in TypeScript, and many names and rules changed, so code written for Cracked will not run here without changes. A few of the differences:

In Cracked Here
__().sine().dac() __().sine().to('main'). Chains end at a named bus
A later line such as __.lowpass() carries on the last chain A chain is a value. You carry on from that value, or select nodes by name
.attr({ frequency: 200 }) .set({ frequency: 200 }) or .frequency(200). See Changing parameters
.start(), .stop() .trigger(), .release(). See Starting and stopping sounds
__.loop(...) and .bind('step', ...) __.transport.sequence(...). See Sequencing

Why a rewrite, and what is new

Cracked keeps everything in one shared place: one set of nodes for the whole page, and a memory of "the last node made". That is quick to type, but two pieces of code on the same page can disturb each other, and timing depends on how busy the page is. The rewrite set out to remove those limits and keep the feel. What that gave:

  • Nothing shared behind your back. Sound lives in an engine that you create, and a page can have more than one. An engine can be divided into scopes, for example one for each track. Code given one track's scope cannot find or change the nodes of another track.
  • Selections that do not get in each other's way. __('lowpass') gives back a selection you can keep in a variable and use again. Using one selection never changes what another one points at. See Selecting nodes.
  • Tight timing. A transport keeps the tempo and schedules each step slightly ahead of time on the audio clock, so notes land on the exact sample even when the page is briefly busy. It runs any number of sequences at once, with different lengths and step sizes (polyrhythm), swing, and tempo changes. See Sequencing.
  • Parameters that describe themselves. Every parameter knows its range, unit, default value and what it does. The node reference on this page is made from that information, and an app can use it to draw the right knob for each parameter.
  • Macros. Several nodes can be wrapped up as one new node type with its own parameters. The built-in polysynth is made this way. See Node types of your own.
  • Changing code while it plays. Run changed code again and only what changed is rebuilt. Everything else keeps sounding, and sequences stay in time. See Re-running code.
  • Offline rendering. The same code can be rendered to audio without playing it, faster than real time, and it comes out the same on every run. See Stems and files. The library's own tests work this way: they render sound in real browsers and check the result.
  • Modern audio processing. Where Cracked ran custom sound code with ScriptProcessor, an older browser feature that shares a thread with the page and can glitch, cracked-up uses AudioWorklet, which runs with the rest of the audio. The bitcrusher, recorder and looper are built on it.
  • Recording and looping. A recorder and a looper that start and stop on the exact sample, live input, and separate files for each part of a mix (stems). See Recording, looping and live input.
  • MIDI. Play a synth from a keyboard, map a controller to a parameter, send notes out, and keep time with other gear in either direction. See MIDI.
  • Running other people's scripts safely. A script can run in a sandbox, a closed-off part of the browser where it cannot read your page, and still play in time. This is what makes sharing scripts between collaborators possible. See Running scripts in a sandbox and the guide Running other people's scripts.
  • Types. The library is written in TypeScript. An editor can complete node names and options as you type, and point out a misspelled one before you run it.
  • The composing helpers are still here. Cracked's small functions for scales, random choices and number conversions are listed under Helpers.

Where it stands

cracked-up is pre-alpha. It is not published to npm, and names and behaviour may still change. Releases are numbered by semantic versioning, starting at 0.1.0; while the number starts with 0, a change that breaks existing code raises the middle number. The repository's CHANGELOG.md lists what changed in each. What this page describes is implemented, and the tests run in Chromium, Firefox and WebKit. Known limits:

  • MIDI is tested with pretend devices only. Its timing has not been measured against real hardware.
  • Safari has no Web MIDI, so MIDI does not work there.
  • Recording from a live microphone is tested in Chromium only.
  • Recordings are kept in memory without compression. There is no mode for very long takes yet.
  • MIDI is not available to scripts running in a sandbox.

The basics

You build sound by chaining nodes. A node makes sound (an oscillator, a sampler) or changes it (a filter, a gain). __() starts a chain; each method adds a node and connects the previous one to it. 

__().saw(110).lowpass(800).gain(0.3).to('main');

That is a sawtooth oscillator at 110 Hz, into a low-pass filter at 800 Hz, into a gain of 0.3, into the output. A chain you do not send anywhere makes no sound.

Give a node an id when you want to reach it later. Pass options as an object; a bare value sets the node's main parameter, so lowpass(800) is short for lowpass({ frequency: 800 }). 

__().saw({ id: 'bass', frequency: 55 })
  .lowpass({ id: 'filter', frequency: 400, q: 8 })
  .gain(0.3)
  .to('main');

Where sound goes: main and other buses

A chain is heard when it ends at a bus: a named point where chains are mixed. main is the bus the engine makes and connects to your speakers. It is stereo (a mono sound is heard on both sides; a panner places it) and cannot be removed. 

__().sine(220).gain(0.2).to('main');
__.bus('main').gain.set(0.5); // overall level

__.bus('drums') makes a bus of your own the first time it is called and returns the same bus after that. A chain reaches it with .to('drums'). Sending to a name no bus has is an error, so a mistyped name is caught at once.

What a bus is made of

Sound passes through a bus in a fixed order. Every picture here is drawn from the code above it. 

__.bus('drums').lowpass({ id: 'tone', frequency: 2000 });
__.bus('drums').gain.set(0.8);

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'snare', buffer: 'snare' }).to('drums');
__.transport.steps('x.x.', () => __('#kick').trigger());
__.transport.steps('..x.', () => __('#snare').trigger());
  1. Input. Everything sent to the bus, mixed.
  2. Inserts. Effects put inside the bus, in the order added. A new bus has none.
  3. Level. bus.gain, one fader for the whole bus.
  4. Output. It goes to the bus's one destination (the heavy line): main, until you name another.

Three things can be done to a bus. Each changes a different part:

You write What it changes What it leaves alone
bus.lowpass(2000)
an insert		 The sound at the output. Everything after the bus gets the filtered sound, and no unfiltered sound is left Where the output goes
bus.to('other'), bus.to(null)
the destination 		Where the output goes: another bus, or nowhere The sound
bus.chain()
a chain from the bus		 Nothing in the bus. A new chain starts, fed a copy of the output (the dashed line), and goes wherever you end it The bus's sound and its destination

Six routings and their graphs

1. One fader for a group

A bus with nothing done to it goes to main.

__.bus('drums').gain.set(0.8);

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'hat', buffer: 'hat' }).to('drums');
__.transport.every('1/4', () => __('sampler').trigger());

You hear the kick and the hat, both at 0.8 of their level.

2. An effect on the whole group: an insert

Call an effect type on the bus and the effect goes inside it. There is no .to to write: the bus's destination is unchanged. 

__.bus('drums')
  .overdrive({ id: 'grit', drive: 0.4 })
  .lowpass({ id: 'tone', frequency: 1200 });

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__.transport.every('1/4', () => __('#kick').trigger());

You hear only the distorted, filtered kick. No clean kick is left anywhere. More in Inserts in detail.

3. A group inside a group: bus.to('other')

The hats get a fader of their own and stay part of the drums. to on a bus sets its destination. 

__.bus('drums').gain.set(0.8);
__.bus('hats').to('drums');
__.bus('hats').gain.set(0.5);

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'hat', buffer: 'hat' }).to('hats');
__.transport.steps('x...', () => __('#kick').trigger());
__.transport.steps('xxxx', () => __('#hat').trigger());

You hear the kick at 0.8 and the hat at 0.5 × 0.8. The hats reach main only through drums, so an insert on drums would process them too.

4. The group, and a processed copy beside it: bus.chain()

The drums as they are, with a heavily compressed copy mixed in under them (parallel compression). bus.chain() starts an ordinary chain fed a copy of the bus's output. Like any chain, it is silent until it ends somewhere. 

__.bus('drums')
  .chain()
  .compressor({ id: 'smash', threshold: -30, ratio: 12 })
  .gain({ id: 'smash-level', gain: 0.5 })
  .to('main');

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'snare', buffer: 'snare' }).to('drums');
__.transport.steps('x.x.', () => __('#kick').trigger());
__.transport.steps('..x.', () => __('#snare').trigger());

You hear two things added in main: the drums untouched (the heavy line) and the compressed copy at half level (the dashed line). Delete the chain and the drums sound exactly as before.

5. Insert or chain: the same effect both ways

The two differ by .chain() and the .to('main') a chain needs. 

__.bus('drums').overdrive({ id: 'crush', drive: 0.8 });

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__.transport.every('1/4', () => __('#kick').trigger());

Insert: you hear the distorted kick, and no clean kick.

__.bus('drums').chain().overdrive({ id: 'crush', drive: 0.8 }).to('main');

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__.transport.every('1/4', () => __('#kick').trigger());

Chain from the bus: you hear the clean kick with the distorted kick on top. Without .to('main'), the clean kick alone: the chain ends nowhere.

.to does two jobs here. On a bus, or straight after an insert, it sets the bus's destination. After .chain() it ends that chain, as on any chain.

6. Heard only through its chains: bus.to(null)

The lows of the drums dry and only the highs echoed: two paths side by side, which inserts cannot do because they come one after another. So two chains from the bus, and to(null) to stop the bus's own output, or the untreated drums would be heard on top. 

const drums = __.bus('drums').to(null);
drums.chain().lowpass({ id: 'lows', frequency: 300 }).to('main');
drums
  .chain()
  .highpass({ id: 'highs', frequency: 300 })
  .tapedelay({ id: 'echo', time: 0.2 })
  .to('main');

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'hat', buffer: 'hat' }).to('drums');
__.transport.steps('x...', () => __('#kick').trigger());
__.transport.steps('..x.', () => __('#hat').trigger());

You hear the two chains and nothing else. Take the chains away and there is silence: a bus sent nowhere is heard only through chains from it.

to(null) has two uses: a bus heard only through two or more chains, as here, and a bus not heard at all, such as one that only feeds a recorder. With one chain, bus.to(null).chain().lowpass(300).to('main') is the insert bus.lowpass(300) the long way round.

Buses in practice

One reverb shared by several sounds. A bus whose only job is the effect: a reverb insert with mix: 1, so the bus carries reverb and nothing else. Each sound goes to main and also sends some of itself to the reverb bus, at its own level. 

__.bus('room').reverb({ id: 'space', seconds: 2, mix: 1 });

__().sampler({ id: 'snare', buffer: 'snare' }).split(
  (dry) => dry.to('main'),
  (send) => send.gain({ id: 'snare-send', gain: 0.4 }).to('room'),
);
__().sampler({ id: 'hat', buffer: 'hat' }).split(
  (dry) => dry.gain(0.5).to('main'),
  (send) => send.gain({ id: 'hat-send', gain: 0.1 }).to('room'),
);

__.transport.steps('..x.', () => __('#snare').trigger());
__.transport.steps('xxxx', () => __('#hat').trigger());

Compressed drums, and a crushed copy underneath. An insert and a chain from the same bus. The copy is taken at the output, after the inserts and the level, so the bitcrusher gets drums that are already compressed. 

__.bus('drums')
  .compressor({ id: 'glue', threshold: -18, ratio: 3 })
  .chain()
  .bitcrusher({ id: 'crush', bits: 4 })
  .gain(0.3)
  .to('main');

__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'snare', buffer: 'snare' }).to('drums');
__.transport.steps('x.x.', () => __('#kick').trigger());
__.transport.steps('..x.', () => __('#snare').trigger());

Recording a group. A chain from the bus that ends at a recorder captures what the bus puts out, inserts and level included. It adds nothing to what you hear, because that chain goes nowhere else. See Recording, looping and live input. 

__.bus('drums').chain().recorder({ id: 'stem', into: 'stem:drums' });

Inserts in detail

An insert is an ordinary node: it has an id, __('#glue') finds it, and it can be set, ramped, bypassed and disposed. It needs an input and an output, so a source or an lfo cannot be one.

bus.gain is the bus's level, so a gain node is inserted through insert(), which has every node type as a method. After a first insert you are already there: 

__.bus('drums').insert().gain(0.5).compressor({ threshold: -18 });
__.bus('drums').compressor({ threshold: -18 }).gain(0.5);   // here gain is the node type

__.bus('drums').inserts;   // a selection of the bus's inserts, in order

bus.inserts is a selection, so one call reaches every effect on the bus. node.insertOf is the bus a node is an insert on, or null. An insert's place in its bus is not a connection: it is not among the node's inputs and outputs. 

__.bus('drums')
  .overdrive({ id: 'grit', drive: 0.6 })
  .lowpass({ id: 'tone', frequency: 900 });
__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__.transport.every('1/4', () => __('#kick').trigger());

// Every second bar, the drums without their effects.
__.transport.sequence('dry', { steps: [0, 1], step: '1 bar' }, (ev) => {
  __.bus('drums').inserts.bypass(ev.value === 1);
});

Inserts are added from the scope that owns the bus. A track's script, or one in a sandbox, can put a compressor on a bus it made but not on main, which belongs to the engine: there, engine.bus('main').compressor() does it.

Bus reference

Call What it does
bus.gain The level, a parameter: bus.gain.set(0.8), a ramp for a fade, or bus.gain.set(v, { glide: 0.02 }) to follow a control
bus.compressor(...), or any effect type Adds an insert after those already there. What it returns takes the next insert, and has to and chain, which act on the bus
bus.insert() The same without adding one, for inserting a gain node
bus.inserts The inserts as a selection, in signal order
bus.to('other'), bus.to(null) Sets the destination, or removes it so that only chains from the bus are heard. bus.to('main') puts it back
bus.chain() Starts a chain fed a copy of the output, after inserts and level. Each call starts another. The bus is not changed
bus.input, bus.output The Web Audio nodes at the two ends, for an app's own analyser. Read only

Running code again. Outside build, each insert call adds another insert. Inside build, a bus ends up as the script describes it this time: unchanged inserts keep their node and state, changed values are set in place, and reordered ones are re-patched. A deleted insert line takes the insert out, a deleted to(...) sends the bus back to main, and a deleted chain from the bus removes its nodes. A build that cannot be applied leaves every bus as it was.

As data. The three are in three places. A chain from a bus is an edge whose from is the bus. Inserts are listed per bus, in order, with no edges. The destination is in the scope's snapshot, null after to(null). 

scope.describe().edges;     // [{ from: 'kick', to: { bus: 'drums' } },            sent to the bus
                            //  { from: { bus: 'drums' }, to: { node: 'smash' } }]  a chain from the bus
scope.describe().inserts;   // { drums: ['grit', 'tone'] }
scope.snapshot().buses;     // [{ name: 'drums', to: 'main', gain: 0.8 }]

// The filter first, then the overdrive. An id left out stops being an insert.
scope.dispatch([{ op: 'bus', name: 'drums', inserts: ['tone', 'grit'] }]);

Applying a saved description puts inserts and chains from buses back on buses that exist. It does not make a bus or set its destination or level; the snapshot has those. The inspector draws a bus's inserts in a row leading into it.

to, connect and modulate

All three make a connection from the end of a chain. They differ in what they connect to.

Method Connects to A string means
.to('main') A bus The bus's name
.connect('#filter') The input of one or more existing nodes A selector that finds the nodes
.modulate('#filter', 'frequency') A parameter of existing nodes, so the signal moves that parameter A selector that finds the nodes

So .to('main') and .connect(engine.bus('main')) do the same thing. to exists because ending a chain at a bus is the common case, and because a string there is a bus name, while a string given to connect is a selector.

To start a new path from a node made earlier, select it and call chain(). 

// Two oscillators into one filter.
__().lowpass({ id: 'filter', frequency: 600 }).gain(0.2).to('main');
__().saw(110).connect('#filter');
__().square(165).connect('#filter');

// A slow sine moves the filter's cutoff by +/- 300 Hz.
__().sine(0.5).gain(300).modulate('#filter', 'frequency');

When something modulates a parameter, its signal is added to the parameter's own value. An oscillator swings between -1 and 1, so a gain after it sets how far the parameter moves.

Selecting nodes

__('selector') finds nodes you have already made and returns them as a selection. Whatever you call on a selection applies to every node in it.

Selector Finds
sampler Every node of that type
#kick The node with that id
.drums, .drums.loud Nodes with that class, or with all of several classes
[role=send], [solo] Nodes with a tag of that value, or with that tag at all
sine, saw Either
sampler:not(.muted) Samplers without the class
gain:nth(1) The second gain, counting from 0 in the order they were made
* Everything, not counting what is inside a macro
polysynth lowpass, #lead > * Nodes inside a macro, which no other selector reaches 
__().sampler({ id: 'kick', buffer: 'kick', class: 'drums' }).to('main');
__().sampler({ id: 'hat', buffer: 'hat', class: 'drums' }).to('main');

__.transport.sequence('beat', { steps: [1, 2], step: '1/4' }, (ev) => {
  __(ev.value === 1 ? '#kick' : '#hat').trigger();
});

Classes and tags are set when a node is made: { class: 'drums loud', tags: { role: 'send' } }.

Branching from nodes you have made: chain()

__('#tone').chain() starts a chain from nodes that already exist: the first node you add after it is fed by every selected node. The selected nodes keep the connections they had, because an output can go to any number of places, so this is how a second path leaves the middle of a first one. Here the filtered saw is heard dry, and a copy of the same filter's output goes through an echo beside it: 

__().saw({ id: 'lead', frequency: 220 }).lowpass({ id: 'tone', frequency: 900 }).gain(0.2).to('main');

// A second path from the filter, written as its own statement.
__('#tone').chain().delay({ time: 0.3, feedback: 0.4, mix: 1 }).gain(0.1).to('main');

With several nodes selected the new node is fed by all of them, so __('.drums').chain().reverb().to('main') mixes every drum into one reverb. The chain belongs to the scope the selection was made in, and is declared again on each build like any other statement. A selection that finds nothing starts a chain fed by nothing, as __() does, and no error says so: check the selector if a branch is silent. A selected node that modulates feeds the parameter it modulates on the new node, as it would in the chain it came from.

Within one statement, .split() makes parallel branches that join again. Use chain() on a selection when the branch does not join the first path, or when it is written somewhere else, such as a later line or a different part of a script that an app edits.

Changing parameters

Every node has parameters, listed in the reference below. Each one has a base value: the value you set, and the one a slider would show.

Call Does
.set({ frequency: 800, q: 4 }) Sets base values
.frequency(800) The same, for one parameter. There is a setter for every parameter name
.set({ frequency: 800 }, { glide: 0.02 }) Moves there over a short time from wherever the value is now. For following a control
.ramp('frequency', 2000, { duration: 2 }) Moves the base value to a target over a number of seconds, from the value it has reached
.offset('frequency', 500, { duration: 0.1 }) Adds an amount on top of the base value for a while, then returns to it

__().saw(110).lowpass({ id: 'filter', frequency: 200, q: 6 }).gain(0.2).to('main');
__('#filter').ramp('frequency', 3000, { duration: 4 });

A macro's parameters take the same calls, and pass each change on to the parameters inside that they drive.

Following a fader

A plain set is an instant step. One step is fine, but a fader or a knob sends a stream of them, dozens a second, and a stream of steps in a level or a pan is heard as crackle (zipper noise). Give set a glide, in seconds, and the value moves to the target in a straight line instead, starting from the value it has actually reached at that moment. That makes it safe to call again while the last move is still on its way: each call takes over from wherever the last one got to, with no jump. 

const level = __.bus('drums').gain;
fader.addEventListener('input', () => {
  level.set(Number(fader.value), { glide: 0.02 });
});

// The same option on a selection and on a setter:
__('#pan').set({ pan: -0.5 }, { glide: 0.02 });
__('#filter').frequency(1200, { glide: 0.05 });

In the live demo the pointer can stand in for the fader:

__().saw(110)
  .lowpass({ id: 'filter', frequency: 600, q: 6 })
  .gain({ id: 'level', gain: 0.2 })
  .to('main');

// Down is quieter, right is brighter. Each move carries on from wherever the last one got to.
mouseMovement(({ x, y }) => {
  __('#level').set({ gain: 0.3 * (1 - y) }, { glide: 0.02 });
  __('#filter').frequency(200 + x * 4000, { glide: 0.05 });
});

About 20 milliseconds is enough to remove the crackle and too short to feel as lag. The parameter's value is the target straight away, and change fires once, with the time the glide ends. Like every operation it takes at, and inside a sequence callback it starts at the step's time. A glide replaces whatever was scheduled for the parameter from its time on. Parameters that cannot be ramped (anything that is not an audio-rate number: a sampler's speed, a switch, a choice) are simply set, so one line of code can serve a control bound to any parameter. setNormalized and reset on a parameter take glide as well. A glide that is negative or not a number is an error.

ramp is for a move you plan: a fade over four seconds, a sweep with an exponential curve, a start value of your own with from. Without from it also starts from the value reached, so a ramp begun while another ramp or a glide is in flight carries on from there, and the earlier one stops. A plain set during a ramp or a glide stops it too, and the value stays where you set it. In each case, what was scheduled to start later is kept. A ramp whose duration or from is not a finite number is refused with an error that names the parameter.

The one exception to the setter rule is a parameter called release (on the compressor): .release() already means "release the note", so that parameter is set with .set({ release: 0.2 }).

The minimum and maximum in the reference are the range a control would cover. They are not limits: you can set a gain of 300 when it is scaling a modulation.

Starting and stopping sounds

.trigger() starts a sound and .release() ends it. What that means depends on the node.

A sampler plays its buffer once per trigger. Each trigger is a new voice, so you never need to stop or rewind it before the next hit. Options given to trigger apply to that hit only. 

__().sampler({ id: 'hat', buffer: 'hat' }).to('main');
__.transport.sequence('hat', { steps: 4, step: '1/8' }, (ev) => {
  __('#hat').trigger({ speed: 1 + ev.index * 0.2, velocity: 0.6 });
});

A sampler's trigger has three options of its own: slice plays one slice of the buffer, duration stops the voice after that many seconds, and velocity is the level of that hit. Any parameter can be given for one hit as well, such as speed, start or reverse. The reference lists them under sampler.

An oscillator runs from the moment it is made and is heard straight away, as a drone. release() closes its gate and trigger() opens it. To make one that is silent until triggered, create it with gate: 'closed'. 

__().square({ id: 'blip', frequency: 660, gate: 'closed' }).gain(0.15).to('main');
__.transport.every('1/4', () => __('#blip').trigger({ duration: 0.08 }));

A macro says for itself what a trigger does, and which options it takes.

Samplers and where their audio comes from

A sampler plays a buffer: a piece of recorded sound held in memory. The engine keeps a store of named buffers, engine.buffers, so the same sound is decoded once and shared by every sampler that uses it.

A sampler's buffer option accepts three things:

You pass What happens
A name already in the store, such as 'kick' That buffer is used
Any other string It is treated as a URL: the file is fetched, decoded, and stored under that URL. The sampler is silent until loading finishes. The server must allow requests from this page.
An AudioBuffer you made or decoded yourself It is used directly

In the live demo, 'kick', 'snare' and 'hat' are not files. The demo page generates them with a few lines of maths when audio starts and adds them to the store by name: 

engine.buffers.add('kick', audioBuffer);

A buffer can be cut into slices by giving it boundaries in seconds. A trigger can then play one slice by number. 

const kit = engine.buffers.get('snare');
kit.slices = [0, 0.03, 0.1, 0.25];
__().sampler({ id: 's', buffer: 'snare' }).to('main');
__.transport.sequence('slices', { steps: [0, 1, 2], step: '1/8' }, (ev) => {
  __('#s').trigger({ slice: ev.value });
});

The rest of this section is about working on a sound: its slices, loop points, giving a sampler another sound, and what an app needs to draw and edit one. Slicing a drum break shows what slices are for.

Changing slices

slices can be set at any time, while samplers play. A trigger reads the list when it is called: a voice that has started, or is scheduled, keeps the region it was given, and the next trigger({ slice }) uses the new list. A slice number past the last slice wraps round. Helpers make a list or change one boundary of it; each returns a new list, in order, with no boundary twice: 

const kit = engine.buffers.get('snare');
kit.slices = sliceGrid(kit.duration, 4);                    // four equal parts
kit.slices = addSlice(kit.slices, 0.01, kit.duration);      // one more boundary, 10 ms in
kit.slices = moveSlice(kit.slices, 2, 0.08, kit.duration);  // the third boundary, to 80 ms
kit.slices = removeSlice(kit.slices, 3);                    // and the fourth is taken out

__().sampler({ id: 's', buffer: 'snare' }).to('main');
__.transport.sequence('slices', { steps: 4, step: '1/8' }, (ev) => {
  __('#s').trigger({ slice: ev.index });
});

moveSlice keeps a boundary between its neighbours, so dragging one never changes the order or the number of slices. sliceAt(kit.slices, 0.05) says which slice holds a time. The store tells you when an entry changes: engine.buffers.on('slices', (ref) => ...) when its boundaries do, and on('ready', ...) when its audio arrives or is replaced. Slices belong to the store entry and not to a sampler: a description of the graph (describe()) names a sampler's buffer and not its slices, so an app that saves a project saves ref.slices beside it. In a sandbox, a script sets them with remote.buffers.setSlices(key, boundaries).

These helpers are listed with the others under Sounds and slices, with normalizeSlices, which puts a list from anywhere in order and inside the sound. sliceByTempo and sliceByOnsets, which make a list from the music, are shown under Slicing a drum break.

Loop points

With loop on, a sampler repeats its region (start to end) until it is released. Give it loopStart and loopEnd, in seconds of the buffer, and only that part repeats: the voice plays from start, and each time it reaches loopEnd it goes back to loopStart. When it is released it stops; it does not play on to end. Here the attack of the snare is heard once and a short piece of its tail is held for as long as the note lasts: 

__().sampler({ id: 'held', buffer: 'snare', loop: true, loopStart: 0.03, loopEnd: 0.05 })
  .gain(0.5)
  .to('main');
__.transport.every('1/2', () => __('#held').trigger({ duration: 0.3 }));

Loop points are kept inside the region, and inside the slice when a trigger plays one. A loopEnd at or before loopStart (both are 0 unless you set them) means the whole region repeats. With reverse, the voice plays down from end and goes round between the same two points. Both points can also be given to one trigger. Their real range, like that of start and end, is the length of the sound: node.buffer.duration.

Another sound for the same sampler

setOption('buffer', ...) points a sampler at another sound and leaves the node, its connections and its parameter values as they are. A voice that is sounding finishes on the sound it started with; the next trigger plays the new one. It accepts what the option accepts when the node is made, takes at like any other operation, and on a selection changes every sampler in it. 

__().sampler({ id: 'drum', buffer: 'kick' }).to('main');
__.transport.sequence('drum', { steps: 8, step: '1/8' }, (ev) => {
  // The same sampler: a snare on steps 2 and 6, a kick on the rest.
  __('#drum').setOption('buffer', ev.index % 4 === 2 ? 'snare' : 'kick').trigger();
});

start, end and the loop points keep their values. An end beyond the new sound stops at its end. A start at or beyond its end leaves nothing to play, so the sampler is silent until start is set lower. When code is re-run with build and only a sampler's buffer has changed, the same thing happens: the sampler is kept and its sound changed in place. Like set, a setOption made in the build after the node has the last word, which is how an app keeps a sound its user picked while the script still names another.

For an app: drawing and editing a sound

The library draws nothing, but it has what a waveform editor for a sampler needs. None of this needs a page except the drawing itself: 

import { createWaveformCache } from 'cracked-up/util';

const node = scope.select('#drum').first();
let sound = node.buffer;                       // the store entry: key, duration, slices, buffer
let cache = sound?.buffer ? createWaveformCache(sound.buffer) : null;

// One lowest and one highest value per pixel column of the visible range.
const { min, max } = cache.peaks({ buckets: canvas.width, start: viewStart, end: viewEnd });

// The real range of start, end, loopStart and loopEnd is the length of the sound.
const length = sound.duration;
node.param('start').set(Math.min(dragged, length));

// Slice markers: sound.slices, changed with addSlice, moveSlice and removeSlice,
// or all at once: sound.slices = sliceByOnsets(sound.buffer, { sensitivity: 0.6 });

// The play cursor, on every animation frame. Empty when nothing sounds.
const heads = [];
function frame() {
  node.playheads(engine.context.currentTime, heads);
  drawCursors(heads);                          // seconds from the start of the sound
  requestAnimationFrame(frame);
}

// What to redraw, and when.
engine.buffers.on('slices', (ref) => { if (ref === sound) drawMarkers(); });
engine.buffers.on('ready', (ref) => { if (ref === sound) cache = createWaveformCache(ref.buffer); });
scope.on('option:changed', (change) => {
  if (change.node === node && change.name === 'buffer') sound = node.buffer;
});

// The user picks another sound: the sampler is kept, its buffer changed.
node.setOption('buffer', 'rimshot');

waveformPeaks reads every sample of the range each time, which is fine for a drum hit. createWaveformCache reads the sound once and then answers in about a millisecond whatever its length (measured: five minutes of stereo, 1000 columns), so use it for anything long that is zoomed and scrolled. playheads works out the positions from what each voice was told (when it started, its region, speed, direction and loop), so it costs almost nothing, and it is exact to within a sample at a steady speed. On a live context, currentTime runs ahead of what is heard by the output latency; ask for currentTime - engine.context.outputLatency for a cursor that matches the ear. Play positions exist only where the audio is: in a sandbox, setOption, the loop points and remote.buffers.setSlices all work, node.buffer has the key, duration and slices, and playheads is always empty.

waveformPeaks, createWaveformCache and detectOnsets take an AudioBuffer or plain channel data with a sample rate, so they also work in a Worker. Asked for rms: true, the first two give the RMS level of each column beside its lowest and highest value.

Slicing a drum break

A break is a few bars of a drummer playing alone. Cut into slices, it becomes a drum kit that keeps the feel of the original playing: you can play the slices in a new order, repeat them, reverse them and change their pitch. Jungle and breakcore are built on this.

The live demo loads one break under the name 'break'. It is Crunchy Drum Break 2 [128bpm] by deadrobotmusic, shared on Freesound under the Creative Commons 0 licence. The demo page fetches it from Freesound when audio starts. If that fails, the page says so, samplers that play 'break' are silent, and everything else works.

The break is 8 bars long at 128 beats per minute, which is 15 seconds. The demo page cuts it into 128 slices, one for every sixteenth note: slice 0 is the first sixteenth of bar 1, slice 16 is the first sixteenth of bar 2, and so on. In every bar the kick drum is on sixteenths 0, 7 and 14, the snare is on 4 and 10, and there is a hi-hat on the other even ones. The odd ones mostly hold the tail of the hit before.

Staying in time

trigger({ slice: n }) plays slice n. A slice of this break lasts one sixteenth note at 128 bpm. To make it last one sixteenth note at your tempo, play it faster or slower by the ratio of the two tempos: speed = your bpm / 128. Then the break follows the transport at any tempo. Like a record, a sample played faster also sounds higher. 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');

// The break was played at 128 bpm. At this speed one slice lasts exactly one step.
const speed = __.transport.bpm / 128;

// 128 steps, one for each slice: the whole break, in order, at your tempo.
__.transport.sequence('break', { steps: 128 }, (ev) => {
  __('#break').trigger({ slice: ev.index, speed });
});

Change the bpm and the break stays in time. A slice number past the last slice wraps round to the start.

Setting the grid

The slices of a buffer are a list of boundaries in seconds. You can replace the list at any time, and there are four ways to make one. These cut the same break in other ways. They are not run from here, because they would change the grid for every other example until you reload the demo: 

const sound = engine.buffers.get('break');

// Equal parts: 64 slices, which for this break are eighth notes.
sound.slices = sliceGrid(sound.duration, 64);

// By tempo: one slice per step at the tempo the break was played at.
sound.slices = sliceByTempo(sound.duration, 128, '1/8');

// By ear: one slice per hit, wherever the hits are.
sound.slices = sliceByOnsets(sound.buffer, { sensitivity: 0.5, minGap: 0.05 });

// By hand: any list of times.
sound.slices = [0, 0.47, 0.94, 1.41, 1.88];

An even grid works for this break because it starts exactly on its first hit, ends exactly on a bar line, and was played to a steady beat. sliceGrid and sliceByTempo take an offset as their last argument for a break whose first hit comes later than 0. For a break that was not played to a steady beat, or whose tempo you do not know, sliceByOnsets listens for where each hit begins: sensitivity, from 0 to 1, is how small a hit counts, and minGap is the least time between two of them, in seconds. The slices then have different lengths, so a pattern of slice numbers plays hits rather than steps. detectOnsets gives the same times without making slices of them. To change one boundary of a list, see Changing slices.

A new order

Give the sequence a pattern of slice numbers and the drummer plays a beat that was never recorded: 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');
const speed = __.transport.bpm / 128;

// Which sixteenth of the first bar to play on each step.
// 0 is a kick, 4 and 10 are snares, 12 is a hat.
const order = [0, 0, 4, 12, 7, 4, 12, 0, 10, 14, 4, 4, 0, 7, 4, 10];

__.transport.sequence('break', { steps: order }, (ev) => {
  __('#break').trigger({ slice: ev.value, speed });
});

Rolls, reverses and pitch

A roll is one hit repeated very fast. ev.at(0.5) is the moment halfway through a step, so several triggers at different fractions of the step make a roll. duration cuts each hit short, reverse: true plays a slice backwards, and multiplying speed changes the pitch: twice the speed is an octave higher and lasts half as long. 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');
const speed = __.transport.bpm / 128;

__.transport.sequence('break', { steps: 16 }, (ev) => {
  const hit = __('#break');
  if (ev.bar % 2 === 1 && ev.index >= 12) {
    // A roll: the snare four times inside each of the last four steps, getting higher.
    for (let i = 0; i < 4; i++) {
      hit.trigger({
        slice: 4,
        at: ev.at(i / 4),
        speed: speed * (1 + (ev.index - 12) / 4),
        duration: ev.duration / 4,
      });
    }
  } else if (ev.index === 6) {
    // Backwards: the sound swells up to the next step.
    hit.trigger({ slice: 4, speed, reverse: true });
  } else if (ev.index === 9) {
    // Twice as fast: an octave higher and half as long.
    hit.trigger({ slice: ev.index, speed: speed * 2 });
  } else {
    hit.trigger({ slice: ev.index, speed });
  }
});

All together: breakcore

Breakcore is fast and restless: the break is cut up, reordered, stuttered and pitched, and it rarely plays the same bar twice. This example has a four-bar phrase. Bar 1 is the break in order with a few tricks. Bar 2 is a new order. Bar 3 is half-time, dark and low. Bar 4 is double-time and ends in a snare roll. A sub bass plays under every kick drum, and now and then a snare is thrown into an echo. The random choices come from a seed, so the phrase is the same each time round. Change the seed, the tempo or a pattern and listen. 

// Breakcore from one drum break: sliced, shuffled, rolled and pitched.
// The sound is "Crunchy Drum Break 2 [128bpm]" by deadrobotmusic (Creative Commons 0):
// https://freesound.org/people/deadrobotmusic/sounds/629052/

__.transport.bpm = 172;

// The break is 8 bars at 128 bpm. The demo page has cut it into 128 slices,
// one for every sixteenth note. Played at this speed a slice lasts exactly one step, so the
// break stays in time at any tempo. Change the bpm above and listen.
const speed = __.transport.bpm / 128;

// --- The sounds ---------------------------------------------------------------
// The drum bus is made gritty and goes through a filter: two inserts, which
// everything sent to the bus passes through.
__.bus('drums')
  .bitcrusher({ bits: 10, rate: 0.6 })
  .lowpass({ id: 'tone', frequency: 14000 });
__().sampler({ id: 'break', buffer: 'break' }).to('drums');

// A second player of the same break, heard only as echoes: a "delay throw".
__().sampler({ id: 'throw', buffer: 'break' })
  .highpass(600)
  .delay({ time: __.transport.seconds('1/8d'), feedback: 0.6, mix: 1 })
  .gain(0.5)
  .to('main');

// A sub bass. It plays under every kick drum, wherever the kick ends up.
__().sine({ id: 'sub', gate: 'closed' }).overdrive(0.5).gain(0.5).to('main');
const bassNotes = [43.65, 43.65, 51.91, 38.89]; // one per bar: F, F, G sharp, D sharp

// --- The plan -----------------------------------------------------------------
// In each bar of the break the kick is on sixteenths 0, 7 and 14, the snare on 4 and 10.
const kicks = [0, 7, 14];
const inOrder = fillArray(16, (i) => i);
const chopped = [0, 0, 4, 7, 7, 4, 2, 0, 10, 14, 4, 4, 0, 7, 4, 10];

// A seed makes the random choices come out the same on every run. Try another number.
const random = createRandom(5);
// The eight eighth notes of a bar, in a random order.
const jumbled = shuffle([0, 2, 4, 6, 8, 10, 12, 14], random).flatMap((s) => [s, s + 1]);

// The phrase is four bars long. Each bar has a pattern and a feel:
// 1 is normal, 0.5 is half-time, 2 is double-time.
const patterns = [inOrder, chopped, inOrder, jumbled];
const feels = [1, 1, 0.5, 2];
// A trick for each step, chosen once, so the phrase has a shape that comes back.
// The first step of a bar is always left alone.
const tricks = fillArray(64, (i) =>
  i % 16 > 0 && chance(0.3, random) ? pick(['roll', 'reverse', 'high', 'gate', 'rest'], random) : 'plain',
);

// Plays one slice. If it holds a kick drum, the sub bass plays with it.
const hit = (slice, at, options) => {
  __('#break').trigger({ slice, at, speed, ...options });
  if (kicks.includes(slice % 16)) __('#sub').trigger({ at, duration: 0.14 });
};

// --- The break ----------------------------------------------------------------
__.transport.sequence('break', { steps: 16 }, (ev) => {
  const bar = ev.bar % 4;
  const step = ev.index;
  const trick = tricks[bar * 16 + step];
  // Use the matching bar of the break, so the drummer's own changes come through.
  const from = 16 * (ev.bar % 8);
  const slice = from + patterns[bar][step];

  if (step === 0) {
    __('#sub').set({ frequency: bassNotes[bar] });
    // The half-time bar is darker.
    __('#tone').set({ frequency: feels[bar] === 0.5 ? 2500 : 14000 });
  }

  if (bar === 3 && step >= 8) {
    // The fill that ends the phrase: a snare roll that gets faster and higher.
    const count = [2, 2, 3, 3, 4, 4, 6, 8][step - 8];
    const rollSpeed = speed * (1 + (step - 8) / 8);
    for (let i = 0; i < count; i++) {
      hit(from + 4, ev.at(i / count), { speed: rollSpeed, duration: ev.duration / count });
    }
  } else if (feels[bar] === 0.5) {
    // Half-time: on every second step, one slice at half speed. It lasts two steps
    // and sounds an octave lower.
    if (step % 2 === 0) hit(from + patterns[bar][step / 2], ev.time, { speed: speed / 2 });
  } else if (feels[bar] === 2) {
    // Double-time: two slices in every step, at twice the speed.
    hit(from + patterns[bar][(step * 2) % 16], ev.time, { speed: speed * 2 });
    hit(from + patterns[bar][(step * 2 + 1) % 16], ev.at(0.5), { speed: speed * 2 });
  } else if (trick === 'roll') {
    // A stutter: the same slice three times inside one step.
    for (let i = 0; i < 3; i++) hit(slice, ev.at(i / 3), { duration: ev.duration / 3 });
  } else if (trick === 'reverse') hit(slice, ev.time, { reverse: true });
  else if (trick === 'high') hit(slice, ev.time, { speed: speed * 2 });
  else if (trick === 'gate') hit(slice, ev.time, { duration: ev.duration * 0.3 });
  else if (trick !== 'rest') hit(slice, ev.time, {});

  // Throw the second snare of bars 2 and 4 into the echo.
  if (bar % 2 === 1 && step === 10) __('#throw').trigger({ slice: from + 4, speed });
});

Time

Most calls take an optional at: the moment the change should happen, in seconds on the audio clock (engine.context.currentTime). Leave it out and the change happens now. Scheduled changes land on the exact sample. 

const now = engine.context.currentTime;
__().sine({ id: 'tone', frequency: 220 }).gain(0.2).to('main');
__('#tone').set({ frequency: 330 }, { at: now + 1 });
__('#tone').set({ frequency: 440 }, { at: now + 2 });

Inside a sequence callback you rarely need at: anything you do there happens at the step's own time. See the next section.

Sequencing: the transport

The transport keeps musical time: a tempo and a position in beats. A sequence is a repeating pattern of steps on it. For each step, your function is called with an event describing that step. You reach it as __.transport. 

__.transport.bpm = 120;
__().sampler({ id: 'kick', buffer: 'kick' }).to('main');

__.transport.sequence('kick', { steps: 'x...x...x..x..x.' }, (ev) => {
  if (ev.value) __('#kick').trigger();
});

steps is the pattern, as an array of numbers or a string. In a string, x means 1 and . means 0, so 'x..x' is the same as [1, 0, 0, 1]. A value of 0 is a rest; your function is still called, which is why the example checks ev.value. Values can be any number, so a step can say which sample to play or what pitch to use.

Option Meaning
steps The pattern. A plain number, such as 5, means that many steps, all with value 1
step How long one step lasts: '1/16' (the default), '1/8', '1/8t' for a triplet, '1/8d' for dotted, or a number of beats
span Use instead of step to spread the steps evenly over a length: { steps: 5, span: '1 bar' } is five in a bar
swing 0.5 is straight. Above 0.5 delays every second step
offset Shifts the whole pattern later by a length
probability Chance, from 0 to 1, that each hit is played
rests false stops your function being called for rests

The event your function receives:

Field Meaning
ev.value The step's value from the pattern
ev.index Which step of the pattern this is, counting from 0
ev.cycle How many times the pattern has repeated
ev.time The exact moment the step sounds, on the audio clock
ev.duration How long the step lasts, in seconds
ev.at(0.5) A moment part-way through the step: 0.5 is halfway. For extra hits between steps
ev.beat, ev.bar Where the step is in the music

Your function runs a fraction of a second before its step is heard, and whatever it does is timed to land exactly on the step. That is why timing stays tight even when the page is busy. It also means a slow function does not make the music late.

Every sequence follows the same transport, so sequences with different step lengths stay locked together. That makes polyrhythms a matter of choosing lengths: 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.5).to('main');

// Four against five in the same bar.
__.transport.sequence('four', { steps: 4, span: '1 bar' }, () => __('#kick').trigger());
__.transport.sequence('five', { steps: 5, span: '1 bar' }, () => __('#hat').trigger());
__().sampler({ id: 'hat', buffer: 'hat' }).to('main');

// A swung pattern with a quick double hit on the last step.
__.transport.sequence('hat', { steps: 'x.xx', step: '1/8', swing: 0.6 }, (ev) => {
  if (!ev.value) return;
  __('#hat').trigger();
  if (ev.index === 3) __('#hat').trigger({ at: ev.at(0.5), velocity: 0.5 });
});

Giving a sequence a name lets you change it: calling __.transport.sequence again with the same name replaces the old one without losing its place. __.transport.every('1/4', fn) calls a function at a regular interval with no pattern, and __.transport.at('2 bars', fn) calls one once.

A sequence that is playing can be changed, read back and followed step by step by code that did not make it, and a function that throws is reported without stopping the music.

Changing a pattern while it plays

__.transport.sequence returns the sequence. Its update changes the pattern, or any other option, and leaves your function as it is. The sequence keeps its place, and the change is heard from the next step. 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');

const seq = __.transport.sequence('kick', { steps: 'x...x...x...x...' }, (ev) => {
  if (ev.value) __('#kick').trigger();
});

// Every two bars, change to the other pattern. The function above is not touched.
const patterns = ['x...x...x...x...', 'x..x..x...x.x...'];
let turn = 0;
__.transport.every('2 bars', () => {
  turn += 1;
  seq.update({ steps: patterns[turn % 2] });
});

seq.setStep(3, 1) changes a single step. Where you do not have the sequence in a variable, __.transport.get('kick') finds it by name, and inside its own function it is ev.sequence, so a pattern can rewrite itself: 

__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.5).to('main');

// A new random pattern each time round.
__.transport.sequence('hat', { steps: 'x.x.x.x.', step: '1/8' }, (ev) => {
  if (ev.value) __('#hat').trigger();
  if (ev.index === 7) {
    ev.sequence.update({ steps: ev.steps.map(() => (Math.random() < 0.6 ? 1 : 0)) });
  }
});

seq.options is the options the sequence was made with, as they were given, so code that did not make a sequence can tell how it was declared: a count reads back as the count, and an array or a pattern string as that array or string, where seq.steps is always the values. After update it is the merged options. setStep does not change it, and it cannot be written to: it is a frozen copy, an array of steps included, and changes go through update. 

const seq = __.transport.sequence('steps', { steps: 16, step: '1/16' }, fn);
seq.options; // { steps: 16, step: '1/16' }
seq.steps; // sixteen 1s

seq.update({ steps: [1, 0, 0, 1] });
seq.options; // { steps: [1, 0, 0, 1], step: '1/16' }
seq.setStep(1, 1);
seq.options.steps; // still [1, 0, 0, 1]
seq.steps; // [1, 1, 0, 1]

__.transport.sequences is every named sequence of the scope, in the order they were first made. Sequences without a name, every and at are not in it. An app uses it to show a grid for each one after running a script, and onDisplay to light the step that is playing: 

await scope.build(script);
for (const sequence of scope.transport.sequences) {
  drawGrid(sequence.name, sequence.steps, sequence.options);
}

Following a sequence's steps

Code that did not make a sequence can follow it: sequence.on('step', listener) calls the listener with the event the sequence's own function gets, and returns a function that stops it. Listeners run before that function for the same step, in the order they were added and with the same time, so a value a listener sets at ev.time is in place when the function triggers a voice that reads it. Here an app gives each step of a script's sequence its own place in the sample: 

await scope.build(script); // declares a sequence called 'steps' that triggers #sampler
const starts = [0, 0.5, 0.25, 0.75];

const stop = scope.transport.get('steps').on('step', (ev) => {
  scope.select('#sampler').set({ start: starts[ev.index] }, { at: ev.time });
});

A listener hears every step the sequence comes to: rests too, even with rests: false, steps that probability drops, and the steps of a muted sequence, whose own function is not called (ev.sequence.muted tells). Like that function it runs ahead of the sound; to draw a playhead when a step is heard, use onDisplay, which waits for it. Steps the transport had to skip because the page fell behind (its late event) are not reported.

Listeners stay with the sequence through update, setStep, restart and a rebuild that declares the same name again, which is the same sequence. They go when the sequence is stopped, cleared, left out of a rebuild or its scope disposed, and a sequence of that name made afterwards is a new one. A build that fails leaves them as they were. To follow sequences whatever becomes of them, listen on the transport: scope.transport.on('step', listener) hears every sequence of the scope, named or not, and engine.transport.on('step', listener) those of every scope. ev.sequence says which one. These run after the sequence's own listeners and still before its function.

A listener that throws is reported like a function that throws, as described below, and the other listeners and the sequence's function still run. Adding the same function twice adds it once. Step listeners belong to the page: for a script in a sandbox, the page listens to the sequence the script declared. 

const stop = scope.transport.on('step', (ev) => {
  const values = perStep[ev.sequence.name];
  if (values) scope.select('#sampler').set({ start: values[ev.index] }, { at: ev.time });
});

Drawing what is heard: onDisplay

A sequence's function and its step listeners run a little ahead of the sound, so that it can be scheduled exactly. That is too early to draw. transport.onDisplay(listener) calls the listener on an animation frame once a step is heard: when the audio clock, less the output device's own delay, has reached the step's ev.time. It is given the same event the sequence's function was given, and returns a function that stops it. Use it to move a playhead or light the step that is playing. 

const stop = engine.transport.onDisplay((ev) => {
  grid(ev.sequence.name).light(ev.index);
});

It reports only the steps whose function ran. A rest left out with rests: false, a step that probability dropped and the steps of a muted sequence are not shown, and neither are every and at. Events are queued only while something listens, so a step scheduled before the listener was added is not reported. Several steps heard since the last frame are reported together on that frame, in time order.

It is a page feature. It needs requestAnimationFrame and a live audio context, so it never calls back during an offline render or where there are no animation frames, and a script in a sandbox does not have it. A listener that throws is logged to the console and the others still run. Listeners are removed when the engine is disposed.

When a callback throws

An error thrown inside the function of a sequence, an every or an at does not stop the transport, and does not stop that function either: it is called again at its next step, and reports again if it throws again. Everything else plays on.

The error goes to the error event of the scope it was scheduled in, and to the engine's. Its origin says where it came from, and gives an app the means to quieten it: 

scope.on('error', (error) => {
  if (error.code !== 'callback') return;
  const { scope, kind, name, sequence } = error.origin;
  // kind: 'sequence', 'every', 'at' or 'listener'. name and sequence are null for every and at.
  show(`${name ?? kind} in ${scope.name}: ${error.message}`);

  // A step listener threw, not the sequence's function: cancel() removes that listener only.
  if (kind === 'listener') return error.origin.cancel();

  // Stop calling it. A muted sequence keeps its place and its steps.
  if (sequence) sequence.muted = true;
  else error.origin.cancel(); // removes an every() for good
});

// A rebuild replaces a named sequence in place, and it stays muted. Lift the mute when the
// script has been changed and built without an error:
await scope.build(script);
for (const sequence of scope.transport.sequences) sequence.muted = false;

For a step listener, origin.sequence and origin.name are those of the sequence it was following. The error's message names the sequence and the scope.

Recording, looping and live input

A recorder sits in a chain, passes the sound through, and records it when triggered. The recording goes into the buffer store under a key, where a sampler can play it. Starting and stopping are exact to the sample, so recorders started together make recordings that line up. 

__().sampler({ id: 'hit', buffer: 'snare' }).recorder({ id: 'rec', into: 'take' }).gain(0.5).to('main');
__().sampler({ id: 'again', buffer: 'take', speed: 0.5 }).to('main');
__.transport.every('1/4', () => __('#hit').trigger());

// Every two bars, record half a bar. Every bar, play the latest take at half speed.
__.transport.every('2 bars', () => __('#rec').trigger({ duration: __.transport.seconds('1/2') }));
__.transport.every('1 bar', () => __('#again').trigger());

Make the recorder before the sampler that plays its key, so the key exists. Each new take replaces the last one under that key; give trigger a key to keep takes apart.

A looper records a loop of a fixed length and plays it round and round. Each later trigger() adds a layer; call('undo') removes the newest and call('clear') empties it. Start the first layer on a bar line and it stays on the bar: the loop is timed against the audio clock itself, so it does not drift, though it will not follow a later change of tempo. 

__().sampler({ id: 'hit', buffer: 'kick' }).looper({ id: 'loop', length: '1 bar' }).gain(0.6).to('main');

// The kick plays for one bar in every four. The looper records that bar and repeats it.
__.transport.sequence('feed', { steps: 'x..x..x.' + '.'.repeat(24), step: '1/8' }, (ev) => {
  if (ev.value) __('#hit').trigger();
});
__.transport.every('4 bars', () => {
  __('#loop').call('clear').trigger();
});

Recording any part of your sound

Recorders and loopers take whatever is connected to them, not just a microphone. The usual way to choose what gets captured is a bus: send any number of chains to it, and start a chain from the bus into the recorder or looper. Nothing is captured until you trigger() the recorder or looper, so a complete example needs three things: the routing, something playing, and a trigger. 

// ROUTING. Anything sent to 'loop-in' can be looped. to(null) stops the bus feeding the
// output by itself, so its one way out is through the looper. Without it you would hear
// everything twice.
__.bus('loop-in').to(null).chain().looper({ id: 'loop', length: '1 bar' }).to('main');

// SOMETHING PLAYING. Two different chains feed the bus: a synth, and a sampler through a filter.
__().polysynth({ id: 'keys', release: 0.2 }).gain(0.5).to('loop-in');
__().sampler({ id: 'hat', buffer: 'hat' }).highpass(5000).gain(0.4).to('loop-in');

// They are only played in the first bar of every four.
__.transport.sequence('keys', { steps: [60, 0, 67, 0, 63, 0, 70, 0], step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 === 0) __('#keys').trigger({ pitch: ev.value, duration: 0.15 });
});
__.transport.sequence('hats', { steps: 'x.xx', step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 === 0) __('#hat').trigger();
});

// A TRIGGER. On that first bar, empty the looper and record. For the other three bars
// nothing is being played: what you hear is the loop.
__.transport.every('4 bars', () => __('#loop').call('clear').trigger());

A recorder is routed the same way. Chained from a bus without to(null) it listens in while the bus plays on as normal, and from main it hears everything: 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().sampler({ id: 'snare', buffer: 'snare' }).gain(0.6).to('main');
__.transport.sequence('kick', { steps: 'x..x..x.', step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 < 2) __('#kick').trigger();
});
__.transport.sequence('snare', { steps: [0, 1], step: '1/4' }, (ev) => {
  if (ev.value && ev.bar % 4 < 2) __('#snare').trigger();
});

// A recorder on the whole mix, and a sampler that plays what it recorded.
__.bus('main').chain().recorder({ id: 'tape', into: 'mix-bar' });
__().sampler({ id: 'tape-play', buffer: 'mix-bar', speed: 0.5 }).to('main');

// The drums play for two bars in every four. Record the second of them, exactly one bar...
__.transport.every('4 bars', () => {
  __('#tape').trigger({ duration: __.transport.seconds('1 bar') });
}, { offset: '1 bar' });
// ...and play it at half speed over the two silent bars.
__.transport.every('4 bars', () => __('#tape-play').trigger(), { offset: '2 bars' });

Recordings and loops stay in time if you start them on a bar line and measure them in bars: start from a transport callback (every('4 bars', ...)), give a recorder duration: __.transport.seconds('1 bar'), and give a looper a length such as '2 bars'. The starter code in the live demo does both.

Layers added to a looper after the first are recorded at its overdub level, 0.7 unless you change it, so that layers stacked on each other do not add up to distortion. Set overdub: 1 to record every layer at full level.

input is a microphone or audio interface. The browser asks for permission the first time. Sound from an input arrives late, by the time it takes to get through the audio hardware and back. Tell a recorder or looper how late with its latency parameter and it shifts what it records to match, so an overdub lines up with what the player heard. A reasonable starting value is engine.context.outputLatency plus the input's own delay; let people adjust it by ear. 

__().input().looper({ id: 'loop', length: '2 bars', latency: 0.02 }).to('main');

Stems and files

To render a piece to separate files, build it on an offline engine, put a recorder on each bus you want a stem of, and render. A take still open when the render ends is finished there, so every stem is as long as the mix. 

import { createEngine } from 'cracked-up';
import { encodeWav } from 'cracked-up/util';

const context = new OfflineAudioContext(2, 48000 * 60, 48000);
const engine = await createEngine({ context });

const drums = engine.scope('drums');
drums.bus('out').chain().recorder({ id: 'stem', into: 'stem:drums' });
// ...build the drums, sending them to 'out', and the other tracks the same way...

engine.select('recorder').trigger({ at: 0 });
engine.transport.start();
const mix = await engine.render();
const drumStem = await engine.buffers.get('stem:drums').ready;

const file = new Blob([encodeWav(mix, { bitDepth: 24 })], { type: 'audio/wav' });

encodeWav writes 16-bit, 24-bit or 32-bit floating-point files from any recording or render.

MIDI

MIDI lives in its own part of the library, cracked-up/midi, and belongs to the page rather than to a script: the page asks for access once and decides what to do with it. It needs a browser with Web MIDI (Chrome, Edge, Firefox; not Safari), and requestMidi fails with a clear message where there is none.

The live demo has done this for you: a midi object is there by that name, and the browser asks you to allow MIDI the first time your code uses it. Each run of the code replaces the listeners and bindings of the run before, and a follow or sendClock that has not changed is left running, so editing the code does not restart the sync. With a keyboard plugged in, this plays a synth from it: 

__().polysynth({ id: 'keys' }).to('main');
midi.play(() => __('#keys'));

// Every note that arrives, whatever it is used for.
midi.on('noteon', (note) => console.log(note.note, note.velocity));

The examples below are written for a page's own code, where midi comes from requestMidi. They work in the demo too with two changes: use __ where they say engine, and where one says await, use .then(...), because a demo script cannot wait. 

import { requestMidi } from 'cracked-up/midi';

const midi = await requestMidi(engine);
midi.inputs;                       // [{ id, name, manufacturer }, ...]
midi.on('devices', () => { /* something was plugged in or removed */ });

Playing and controlling

// Notes from a keyboard play a synth: note-on triggers the pitch, note-off releases it.
engine.chain().polysynth({ id: 'keys' }).to('main');
midi.play(() => engine.select('#keys'));

// Any message, on any channel, with as many listeners as you like.
midi.on('noteon', (note) => console.log(note.note, note.velocity, note.channel), { channel: 10 });
midi.on('pitchbend', (bend) => engine.select('#keys').set({ detune: bend.value * 200 }));

// Tie a knob to a parameter. The knob's travel covers the parameter's control range.
midi.bind({ controller: 74 }, () => engine.select('#filter').param('frequency'));

// Or let the person choose the knob: this waits for the next one they move.
const binding = await midi.learn(() => engine.select('#filter').param('frequency'));
binding.remove();

Give bind and learn a function that finds the parameter, as above, rather than the parameter itself. Then the knob keeps working after code is re-run and the node behind it has been replaced.

Sending notes

const out = midi.output('My Synth');   // by name or id; the first output if you give none
out.channel = 2;

engine.transport.sequence('bass', { steps: [36, 0, 36, 43], step: '1/8' }, (ev) => {
  // No time given: inside a sequence it lands exactly on the step.
  if (ev.value) out.note(ev.value, { duration: ev.duration * 0.8, velocity: 0.9 });
});
out.cc(1, 0.5);
out.pitchBend(-1);

Keeping time with other gear

// Other gear follows this page: clock pulses, Start, Stop, and where to continue from.
const stopSending = midi.sendClock('Drum Machine');

// This page follows other gear: its Start and Stop, its tempo, its position.
const follow = midi.follow('Drum Machine');
follow.bpm;      // the tempo measured from the incoming clock
follow.error;    // how far the transport is from the clock right now, in seconds
follow.stop();   // go back to the transport's own tempo

While following, setting transport.bpm does nothing, so code that sets a tempo can be re-run without fighting the clock. Timing is matched to what is heard, not to what has been computed: notes and clock sent out are delayed by the audio output's latency, so a drum machine and the page's own sound line up at the speakers.

How tight is it? With a pretend clock whose pulses each arrive up to 1.5 milliseconds early or late, the transport stays within 2 milliseconds of it at 70, 120 and 174 bpm, and comes back onto the clock after a tempo change. That has been measured with simulated and in-browser clocks only. It has not yet been measured against real hardware, where the MIDI interface and driver add their own delay and unevenness.

Code that is run again and again

A script that is re-run on every edit would add its listeners again each time, and would start following the clock afresh, which takes about a beat to settle. Run it through midi.build and its calls replace the ones the last run made. Listeners, bindings and play are swapped. A follow or sendClock with the same arguments as one already running is kept, with the tempo it has measured. Calls the new run no longer makes are stopped, and if the run throws, nothing changes. This is what the live demo does. 

// Each time the script changes:
midi.build((midi) => runScript(midi));

// Or in two steps, when you only know later whether the run worked:
const session = midi.session();
runScript(session.midi);
if (ok) session.commit();
else session.rollback();

Interaction: keys and the mouse

A script can be played from the computer keyboard and the mouse. keyPress and keyRelease call a function when a key goes down or comes up, and mouseMovement calls one as the pointer moves, with its place on the page as two numbers from 0 to 1. Cracked had the first and the last as key_press and mouse_movement; those names work here too. 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().saw({ id: 'lead', gate: 'closed' })
  .lowpass({ id: 'filter', frequency: 800, q: 8 })
  .gain(0.2)
  .to('main');

// Click outside the editor first: keys typed into the editor are left alone.
// Space plays the kick, and A S D F G hold notes for as long as they are down.
const notes = { a: 220, s: 247, d: 277, f: 330, g: 370 };
keyPress(({ key }) => {
  if (key === ' ') __('#kick').trigger();
  if (notes[key]) __('#lead').set({ frequency: notes[key] }).trigger();
});
keyRelease(({ key }) => {
  if (notes[key]) __('#lead').release();
});

// Left to right opens the filter. Towards the top makes it ring.
mouseMovement(({ x, y }) => {
  __('#filter').set({ frequency: 200 + x * 5000, q: 1 + (1 - y) * 15 });
});

Three things differ from Cracked. The callback is given an object with the useful parts picked out (key, code, x, y) and the browser's own event as event. Each helper returns a function that stops it. And keys typed into a text box or the editor do not call back, so that typing code does not play the code being typed.

In the live demo, each run of the code replaces the listeners of the run before, so re-running does not pile them up. In an app of your own, createInteraction() from cracked-up/util gives the three helpers and a clear() that removes everything added through it; make one for each run of a script and clear the one before. Pass an element to listen to just that element, with x and y measured across it. These helpers listen to the page, so a sandboxed script cannot use them: the sandbox has no page of its own. 

import { createInteraction } from 'cracked-up/util';

let interaction = null;
function run(code) {
  const next = createInteraction();
  const program = new Function('__', ...Object.keys(next.helpers), code);
  program(__, ...Object.values(next.helpers));
  interaction?.clear();
  interaction = next;
}

Bypassing a node

A bypassed effect passes its input straight to its output. A bypassed source, or a modulator, is silent. The node keeps running while bypassed, so a delay keeps its contents and an oscillator keeps its phase. The switch is a 5 millisecond crossfade, so it does not click. 

__().saw(110).lowpass({ id: 'filter', frequency: 300, q: 8 }).gain(0.2).to('main');

// Take the filter out on every second beat.
__.transport.sequence('toggle', { steps: [0, 1], step: '1/4' }, (ev) => {
  __('#filter').bypass(ev.value === 1);
});

.bypass() turns the bypass on, .bypass(false) turns it off, and { bypass: true } among a node's options makes it bypassed from the start.

Node types of your own: macros

A macro gives a name to a chain you keep writing, so you can make it like a built-in node: __().blip(). It has a few parameters of its own, and each one drives parameters of the nodes inside. From outside it is one node: you select it, set it, trigger it and connect it like any other. The built-in polysynth, multiband and tapedelay are macros. 

define({
  type: 'blip',
  params: {
    pitch: { default: 440, min: 50, max: 4000,
             drives: [{ select: '#tone', param: 'frequency' }] },
  },
  build(__) {
    __().sine({ id: 'tone', gate: 'closed' }).gain(0.2).to('out');
  },
  trigger(__) {
    __('#tone').trigger({ duration: 0.08 });
  },
});

__().blip({ id: 'blip' }).to('main');
__.transport.sequence('blips', { steps: 'x..x..x.' }, (ev) => {
  if (ev.value) __('#blip').set({ pitch: 440 + 110 * ev.index }).trigger();
});

build makes the inside, in a scope that belongs to this one blip. What it sends to out is the blip's output. pitch is the blip's own parameter: setting it sets the frequency of the sine inside. trigger says what .trigger() does to a blip. Change the 110 and the tune changes while it plays.

define is a name the live demo and the sandboxed demo give to scripts. In a page of your own, make the definition with defineMacro and give it to the engine, when you create it or later. From then on every chain, bus and scope of that engine has the type. 

import { createEngine, defineMacro } from 'cracked-up';

const blip = defineMacro({ type: 'blip', params: {}, build(__) { /* ... */ } });

const engine = await createEngine({ context: new AudioContext(), nodes: [blip] });
// or, on an engine you already have:
engine.registry.register(blip);

// What the demo's define is:
const define = (definition) => engine.registry.register(defineMacro(definition));

A bigger one: a drum

A macro earns its keep when one number has to move several things at once. This drum is a sine that drops in pitch, with a burst of filtered noise for the stick. It has three parameters, and each drives two inner ones. The script makes two drums from it, tunes them apart, and plays them from sequences. 

define({
  type: 'drum',
  description: 'A tuned drum: a sine that drops in pitch, with a click of noise.',
  params: {
    // One number tunes the whole drum: the body as given, the click's filter 8 times up.
    tune: {
      default: 60, min: 30, max: 400, unit: 'hz', curve: 'log',
      drives: [
        { select: '#body', param: 'frequency' },
        { select: '#snap', param: 'frequency', scale: { multiply: 8 } },
      ],
    },
    // Seconds for the body to die away. The click takes a fifth as long.
    decay: {
      default: 0.3, min: 0.03, max: 2, unit: 'seconds', curve: 'exp', rate: 'control',
      drives: [
        { select: '#shape', param: 'decay' },
        { select: '#tick', param: 'decay', scale: { multiply: 0.2 } },
      ],
    },
    // 0 is dull, 1 is bright: opens the filter along a curve, and brings up the click.
    tone: {
      default: 0.5, min: 0, max: 1,
      drives: [
        { select: '#lid', param: 'frequency', scale: (tone) => 200 * 2 ** (tone * 6) },
        { select: '#click', param: 'gain', scale: { multiply: 0.5 } },
      ],
    },
  },
  triggerOptions: {
    velocity: { type: 'number', default: '1', description: 'How hard the drum is hit.' },
  },
  build(__) {
    __().lowpass({ id: 'lid' }).gain(0.4).to('out');
    __().sine({ id: 'body' })
      .adsr({ id: 'shape', attack: 0.001, sustain: 0 }).connect('#lid');
    __().noise().bandpass({ id: 'snap', q: 2 })
      .adsr({ id: 'tick', attack: 0.001, sustain: 0 })
      .gain({ id: 'click' }).connect('#lid');
  },
  trigger(__, options, macro) {
    const velocity = options.velocity ?? 1;
    const hz = macro.value('tune');
    // A harder hit starts further above the note, then falls to it.
    const from = hz * (1 + 3 * velocity);
    __('#body').ramp('frequency', hz, { from, duration: 0.05, curve: 'exp' });
    __('adsr').trigger({ velocity });
  },
});

// Two drums from one definition, each with its own settings.
__().drum({ id: 'kick', class: 'kit', tune: 50, decay: 0.35, tone: 0.2 }).to('main');
__().drum({ id: 'tom', class: 'kit', tune: 140, decay: 0.15 }).gain(0.6).to('main');

// From outside: a slow lfo bends the tom's tuning.
__().lfo({ frequency: 0.25, depth: 12 }).modulate('#tom', 'tune');

__.transport.sequence('kick', { steps: 'x..x..x.' }, (ev) => {
  if (ev.value) __('#kick').trigger();
});
__.transport.sequence('tom', { steps: euclid(5, 16), step: '1/16' }, (ev) => {
  if (ev.value) __('#tom').trigger({ velocity: 0.4 + 0.2 * (ev.index % 4) });
});
// Every bar the whole kit glides duller or brighter.
__.transport.sequence('tone', { steps: [0.2, 0.9], step: '1 bar' }, (ev) => {
  __('.kit').set({ tone: ev.value }, { glide: 1 });
});
  • One parameter, several targets. Each entry in drives names inner nodes with a selector and one of their parameters. scale converts the value on the way: { multiply, add } for a straight line, or a function for a curve, as tone does to get from 0 to 1 to 200 to 12,800 Hz.
  • Starting values. When a drum is made, each of its parameters is given its value, from the call or its default, and passes it on. So lowpass({ id: 'lid' }) needs no frequency of its own: tone sets it.
  • Options for one hit. Whatever is given to .trigger({ ... }) arrives as options. What they mean is up to the macro: here velocity is passed on to both envelopes and sets how far the pitch drops. triggerOptions only documents them, for the reference and the editor.
  • Reading its own settings. macro.value('tune') is the drum's tuning at the time of this hit, whatever the script last set it to.
  • Time. Nothing in trigger names a time. Inside a macro's functions, whatever you do happens at the time of the call that got you there, so a drum triggered from a sequence lands on the step.
  • Two instances. Each drum has its own inside, so the ids in build never clash. '#tom' finds one drum, '.kit' both.
  • From outside. The lfo is connected to tune as to any parameter, and the last sequence sets tone with a glide, which glides the filter and the click level inside each drum.

type The name, which becomes a method of chains and buses. Letters, digits, _ and -, starting with a letter or _, and not a name chains already use, such as to or connect
params The macro's own parameters by name, as in the next table. Required; {} for none
build(__, init, macro) Makes the inside. __ is a scope of this instance alone, with two buses already in it. Send to 'out' and that is the macro's output. For an effect, continue from __.bus('in').chain(), which is whatever is connected to the macro. init holds every option the node was made with that is not one of its parameters. Returns nothing
trigger(__, options, macro) What .trigger(options) does. options.at is the time of the trigger. A macro without it can still be called with .trigger(), which then does nothing
release(__, options, macro) What .release(options) does
methods Operations of its own by name, each (__, args, at, macro) => { ... }, reached with .call(name, args)
shorthand The parameter a bare argument sets, so that .blip(660) works. It has to be one of params
description One line saying what it is, for the reference and the editor
category Where it is listed: 'source', 'filter', 'synth' and so on. 'utility' if left out
options, triggerOptions Documents the options build reads from init and the ones trigger accepts, each as { type, default, description }. Nothing is checked against them

Field What it is

choices A list of strings makes it a choice among them, and default one of them

A method is for anything a macro can do that is not a trigger. It runs at the time the call is given, or the step's time inside a sequence callback: 

define({
  type: 'sweeper',
  params: {},
  build(__) {
    __.bus('in').chain().lowpass({ id: 'filter', frequency: 400 }).to('out');
  },
  methods: {
    sweep(__, args) {
      __('#filter').ramp('frequency', args.to ?? 4000, { duration: 0.5, curve: 'exp' });
    },
  },
});

__().saw(110).sweeper({ id: 'sweep' }).gain(0.2).to('main');
__('#sweep').call('sweep', { to: 6000 });

A macro from outside

  • Selecting. A macro is one node. __('drum'), __('#kick') and __('.kit') find it, and * counts it once. The nodes inside are not found by a plain selector, so __('adsr') finds none of a drum's envelopes. Reach them through the macro: __('#kick #lid'), __('drum adsr'), __('#kick > *'), or __('#kick').select('#lid'). What you set that way lasts until the macro's own parameter next sets it.
  • set, ramp and glide. They work as on any parameter, and there is a setter for each name: __('#kick').tune(45). A set is passed to every inner parameter the macro's parameter drives, converted by its scale. A ramp or a glide moves each of them to its own converted target over the same time. A glide steps an inner parameter that cannot ramp, such as an envelope's decay, and a ramp of one is refused. A value an inner parameter refuses is refused by the macro's, with the inner node named in the error.
  • Modulating. A signal can be connected to a macro's parameter where it drives an audio-rate parameter with no scale, and it reaches only those. On the tom, the lfo bends the body and not the click's filter. A parameter with nothing of that kind cannot be modulated.
  • Connecting. A macro has an output if its build sent anything to out, and an input if it took a chain from in. One with both is an effect: put it in a chain, or on a bus as an insert with __.bus('drums').sweeper(). Nothing inside can reach a bus outside, main included.
  • Nesting. A macro's build can make other macros. Each level is one more step in a selector: __('#outer #inner lowpass').
  • As data. describe() and snapshot() list a macro as one node with its own parameters, without what is inside. node.insideScope is the scope build filled, for an app that wants to look: node.insideScope.describe(). The inspector opens a macro in place.
  • In the editor. The editor completes the fields of a definition inside define({ }) and defineMacro({ }), and out and in as bus names inside it. A type a script defines is offered after a chain, with the parameters written in its params, as soon as it is typed.

Changing a definition

Registering a type under a name that is taken replaces it, a built-in included. Nodes already made from the old definition keep working as they were made.

That matters when code is run again. A rebuild keeps a node whose type, id and creation options are the same, and for a macro that means it keeps the inside it was built with, and its old trigger. So in the live demo a change to a number where a drum is made is heard at once, and a change inside define({ ... }) is not heard until the instance is made anew, which giving it another id does. A script in a sandbox does not have this to think about. There an instance is replaced when what the definition's build makes, its parameters or the names of its methods change, and trigger, release and the methods are always the ones last defined.

Re-running code: build

A scope's build runs a function that makes nodes, connections and sequences, and then makes the scope match what the function asked for. Run it again with changed code and only the difference is applied:

  • A node that is asked for again is kept and keeps sounding. Changed parameter values are set on it in place.
  • A node is recognised by its id. A node without one is recognised by its position among the nodes of its type: the second lowpass your code makes is the second lowpass it made last time. Give a node an id if you want it to survive being moved around. node.autoId is true for a node that was given no id, so an app can tell which nodes are known only by their position.
  • A node is replaced only if its type or one of its creation options (an oscillator's gate, a sampler's choke) changed. A sampler's buffer is the exception: it is changed in place.
  • A macro is kept by the same rule, with the inside it was built with, even if its definition has changed since. See Changing a definition.
  • Nodes, connections and sequences the function no longer asks for are removed.
  • A sequence with a name is replaced in place and stays in time. Give sequences names.
  • A build happens whole or not at all. If the function throws, or asks for anything that cannot be done, nothing it asked for happens and the scope plays on as it was. See below. 
const scope = engine.scope('track-1');

await scope.build((__) => {
  __().saw({ id: 'bass' }).lowpass(500).gain(0.25).to('main');
});

// Later: the saw and the gain are untouched, the filter moves to 900 Hz, a delay is added.
const result = await scope.build((__) => {
  __().saw({ id: 'bass' }).lowpass(900).delay(0.25).gain(0.25).to('main');
});
result.added;     // [delay]
result.updated;   // [lowpass, gain]  (the gain's input changed)
result.unchanged; // [saw]

The live demo runs your code through build on every key up. A rebuild sets every parameter back to what the code says, so a value changed from a sequence callback lasts until the next rebuild. A set or ramp the code itself makes after asking for a node has the last word on every run, the first and the ones after it alike.

When a build cannot be applied

build returns a promise. If everything the function asked for can be done, it is done and the promise resolves with what changed. If anything cannot, the promise rejects with the first error and nothing has changed: not the nodes, their values, the connections, the buses with their inserts and routes, the sequences with their step listeners, nor the tempo, and the scope has emitted no param:changed, node:added or node:removed. An app can tell its user that the last version that worked is still the one playing, and that is exactly true. 

try {
  await scope.build((__) => {
    __().saw({ id: 'bass' }).lowpass(1200).gain(0.25).to('main'); // fine
    __('#bass').set({ frequency: 'loud' });                       // not a number
  });
} catch (error) {
  error.message; // "frequency" on saw "bass" needs a finite number, got "loud".
  error.nodeId;  // 'bass'
  // The filter is still where it was.
}

What refuses a build:

  • the function throwing, for any reason;
  • a value of the wrong kind, for a new node or one being kept, in its options or through set, a shortcut setter, ramp or offset: text for a number, a number that is not finite, a choice the parameter does not have;
  • a node that cannot be built, including one that replaces a kept node because a creation option changed, and a macro whose own build throws;
  • a connection, a bus route or an insert that cannot be made: a node or bus that does not exist, a node with no input, a parameter that cannot be modulated;
  • an id used twice, a method a node does not have;
  • sequence options or a tempo that make no sense.

A number outside a parameter's min and max is not an error: that range is what a control covers, not a limit.

To keep that promise the library holds back what your function asks of anything that was already there. A set, ramp, trigger or bypass on a kept node, and a kept bus's to() or gain, are checked on the spot and carried out when the function has returned, in the order you wrote them. The one thing you can notice: inside the function, param.value of a kept node still reads the old value after you set it. New nodes are made, set and connected straight away.

result.errors is nearly always empty. It lists only what a node's own code threw while a successful build was being carried out: a trigger, release or method your function called on a kept node, or a custom parameter's handler. Nothing can try those beforehand, so they are reported and the rest of the build stands.

Not undone when a build is refused: the transport being started, stopped or moved from inside the function, buffers loaded there, and node types registered there. A listener of the transport's tempo event hears a tempo the function set, and then the old one again.

A build of another scope started inside the function is part of the outer build: it is applied when the outer one succeeds and not at all when it is refused. For a node a build adds, the scope emits node:added first and its param:changed after.

scope.apply(graph) does the same from data instead of code: scope.describe() returns a scope's nodes and connections as plain JSON, and apply makes a scope match such a description. That is how a host saves and restores a graph, or edits one from a user interface.

apply is not all or nothing. It works node by node: a node that cannot be made as described, or whose values cannot all be set, is left exactly as it was, a connection that cannot be made is left out, and each is listed in result.errors while the rest of the description is applied. A saved graph with one stale entry still loads.

Inspecting the graph

cracked-up/inspect draws a scope as a graph, for finding out why something is silent or where a level goes wrong. Every node is a box, every bus a rounded shape, and signal runs from left to right. Each output has a level meter, and a connection moves only while signal is going through it, so a silent path looks still. It is for a page's own code, not for the live demo; the inspector page shows it running. 

import { toggleInspector } from 'cracked-up/inspect';

// A sidebar with a close button. The same call closes it again.
button.addEventListener('click', () => toggleInspector(engine, { mode: 'sidebar' }));

openInspector(target, { mode }) is the same without the toggling, and mode: 'modal' opens a window over the page. For a layout of your own, such as a panel or a popup window, createInspector draws into an element you give it: 

import { createInspector } from 'cracked-up/inspect';

const inspector = createInspector(engine, { parent: document.querySelector('#graph') });

inspector.setScope(engine.scope('drums'));     // show one scope
inspector.select(engine.select('#filter').first());  // open a node's details
inspector.fit();                               // bring the whole graph into view
inspector.destroy();                           // remove it, and everything it attached

Give it an engine and it shows everything, with each child scope opened as a frame inside the root. Give it a scope and it shows only that scope.

Meters

The meter on a node shows the level at its output from -60 dB to full scale: the solid part is the RMS level, the lighter part the peak, and the mark is the highest peak of the last second, which turns red once a peak has gone over full scale. All channels are mixed to one for the reading, so a sound panned hard to one side reads 6 dB low.

Modulators, and everything else whose output only ends up in parameters, are not sound, and decibels say little about them: a 2 Hz wave would read as a level that pumps twice a second. Their meter has zero in the middle and shows the range the value has covered in the last two seconds and where it is now. A connection from one of them moves while the value is changing and stays still while it is steady.

Levels are read by connecting an AnalyserNode to an output. The analyser leads nowhere, so it adds nothing to what you hear and delays nothing; a test renders the same graph with an analyser on every output and without, and the two renders are the same sample for sample. Only outputs that are on screen are listened to, only while audio is running, and destroy() removes them all. In headless Chromium on a laptop the inspector's script took 0.3 ms per frame with 20 nodes in view and 0.85 ms with 100, at a steady 60 frames a second.

A node's details

Clicking a node opens a panel with its description and parameters from the reference, their current values, what is connected to it, a larger meter, a waveform and a spectrum of its output. For a modulator the panel shows the value over the last four seconds instead. There is a bypass switch, and a Trigger button on nodes that can be triggered, except recorders and loopers, where a trigger would record.

Values shown are the ones that were set. A ramp in flight, an offset, or modulation does not show in the number. A modulated parameter names what moves it and the range that signal is covering.

While the graph changes

The inspector follows the scope. It hears about nodes that come and go, and reads the graph again a few times a second for changes that send no event, such as a new connection or a bypass. After a build, nodes that were kept stay where they are and new ones are fitted into the gaps; the pan, the zoom and whatever was opened are left alone. Tidy lays everything out afresh. It works on a suspended context, with the meters idle, and on an offline engine, where it draws the graph and listens to nothing.

Running scripts in a sandbox

Code from someone else should not run in your page, where it could read the page, its storage and the signed-in session. cracked-up/remote lets the same code run somewhere it can do no harm, such as a frame with sandbox="allow-scripts", while the engine stays in the page.

Inside the sandbox, createRemote gives the script the same __. It has no audio behind it: reads are answered from a copy of the scope's state, and everything the script does is sent to the page as plain-data commands. In the page, linkRemote applies those commands to one scope and nothing else. Sequence callbacks run in the sandbox: the page sends each step a little ahead of time, and the commands the callback makes land exactly on the step. 

// In the page
import { linkRemote } from 'cracked-up/remote';

const link = linkRemote(engine.scope('guest'), {
  send: (message) => frame.contentWindow.postMessage(message, '*'),
  allow: (command) => command.op !== 'loadBuffer',   // refuse what you do not want
});
frame.contentWindow.postMessage({ init: link.state() }, '*');
window.addEventListener('message', (event) => {
  if (event.source === frame.contentWindow) link.receive(event.data);
});

// In the sandboxed frame
import { createRemote } from 'cracked-up/remote';

const remote = createRemote({ ...state, send: (message) => parent.postMessage(message, '*') });
window.addEventListener('message', (event) => remote.receive(event.data));

remote.build((__) => {
  __().sampler({ id: 'kick', buffer: 'kick' }).to('main');
  __.transport.sequence('kick', { steps: 'x...' }, (ev) => {
    if (ev.value) __('#kick').trigger();
  });
});

What differs from running next to the engine:

  • Outside a sequence callback there is no clock, so an operation without a time happens when it reaches the page.
  • A script can send audio to an outer bus such as main, but cannot change that bus or put inserts on it, and cannot select or change nodes outside its scope. Inserts on its own buses work as they do next to the engine.
  • Nodes inside a macro can be written to (__('polysynth lowpass').set(...)) but not read: the sandbox's copy does not include them.
  • There is no transport position to read, and a script cannot start or stop the transport. Sequence events carry the beat and bar.
  • Step listeners belong to the page. sequence.on('step') and transport.on('step') throw in the sandbox. On the page, scope.transport.get(name).on('step', listener) follows a sequence the script declared, and runs before the step is sent to the script. See Following a sequence's steps.
  • __.transport.sequences is not there. __.transport.get(name) is, and a sequence's options, update and setStep work as they do next to the engine.
  • A sampler's play positions exist only where the audio is: playheads() is always empty, and node.buffer has the key, duration and slices without the audio. setOption('buffer', ...), the loop points and set with glide work the same.
  • remote.build is all or nothing like scope.build, but it returns nothing to wait for. A value of the wrong kind is refused in the sandbox: build throws and nothing is sent. What only the page can know (a bus that does not exist, a node it cannot build) is refused there: the page applies none of the build, the reason arrives at remote.on('error'), and the sandbox goes back to the nodes, sequences and callbacks it had before. Commands sent outside a build are still applied one by one.

A script can define its own node types with remote.define, which takes the same definition as defineMacro: see Node types of your own. The inner graph is built in the sandbox and sent to the page as data. The macro's trigger, release and methods stay in the sandbox and run there whenever anyone calls them, including a control in the page. One difference: a drive's scale has to be data, such as { multiply: 1.01 }, because a function cannot be sent to the page. And a script cannot redefine a type the page already has.

remote.buffers.get(key) gives a loaded buffer's duration and slice boundaries, and remote.buffers.load(url) asks the page to load one, which the page may refuse. remote.buffers.setSlices(key, boundaries) replaces a buffer's slices. That reaches the page as a slices command, and setOption as an option command; like loadBuffer, the page can refuse either in allow.

The frame keeps a script away from your page, not from the network or the processor. Give the frame a content security policy to stop it making requests, and expect that a script stuck in a loop stops its own sequences. The sandboxed demo shows all of this running, with the measured round-trip time. The guide Running other people's scripts covers when an app needs this, how to set it up safely, and what to share between collaborators.

The editor

cracked-up/editor is a code editor for cracked-up scripts, for an app to embed. It is the editor in the live demo. It completes node types (after a chain, and after a bus for its inserts), parameters, selectors, buffer and bus names, helpers and the arguments of functions an app adds, shows what each is when you hover, and shows the source of a node type or helper when you Cmd-click it (Ctrl-click outside macOS), or press F12 on it.

It is built on CodeMirror 6, which is not bundled with the library and not installed with it. The other entry points do not import it. An app that uses the editor installs the CodeMirror packages itself: 

npm install @codemirror/state @codemirror/view @codemirror/commands @codemirror/language \
  @codemirror/autocomplete @codemirror/lang-javascript @lezer/highlight @lezer/common

The editor is plain DOM: give it an element and it fills it. It keeps nothing global, so a page can hold any number of them, and destroy() removes everything one added. A minimal host: 

import { createEngine } from 'cracked-up';
import { helpers, wrapUserCode } from 'cracked-up/util';
import { createEditor, catalogFromEngine } from 'cracked-up/editor';

const engine = await createEngine({ context: new AudioContext() });
const scope = engine.scope('script');

const editor = createEditor({
  parent: document.querySelector('#code'),
  doc: "__().sine(220).gain(0.2).to('main');",
  catalog: catalogFromEngine(engine),
  // Cmd-Enter runs the script. onChange is there too, for running on every edit.
  keymap: [{ key: 'Mod-Enter', run: () => (run(), true) }],
});

async function run() {
  try {
    const program = new Function('__', ...Object.keys(helpers), wrapUserCode(editor.value));
    const result = await scope.build((__) => program(__, ...Object.values(helpers)));
    editor.showError(result.errors[0] ?? null);
  } catch (error) {
    editor.showError(error);
  }
}

The catalog

The editor needs no engine. Everything it knows comes from a catalog, which is plain data: the node types (as engine.registry.list() gives them), the helpers, the buffers with their slice counts, and names that exist outside the document, such as the ids, classes, buses and sequences of another track's script. It adds what it finds in its own document: every id and class, every bus('name') and named sequence, and node types the script defines itself. 

editor.setCatalog({
  types: engine.registry.list(),
  buffers: [{ key: 'kick' }, { key: 'break', slices: 128 }],
  // nodes other scripts made; with a type, the editor knows an id's parameters
  ids: ['lead', { name: 'pad', type: 'polysynth', description: 'The pad on track 2.' }],
  classes: ['drums'],
  // a name, or a name with what it is for, shown in completion and on hover
  buses: ['drums', { name: 'reverb-send', description: 'The shared reverb. Send to it, quietly.' }],
  sequences: ['intro', { name: 'fill', description: 'One bar, every eighth bar.' }],
  globals: [
    { name: 'engine', description: 'The engine.' },
    // kind says what a name is, so its members are completed: midi.follow(), midi.output().note()
    { name: 'midi', kind: 'midi', description: 'MIDI in and out.' },
  ],
  midiInputs: midi.inputs.map((port) => port.name),    // offered where a port is named
  midiOutputs: midi.outputs.map((port) => port.name),
  // helpers: left out, the library's own are used. To offer keyPress and mouseMovement as well:
  // helpers: [...builtinHelpers(), ...INTERACTION_DOCS]
});

The catalog changes while people type: samples load, macros get defined. Call setCatalog again whenever it does. When several editors show scripts of one project, give them all one store and change that: 

import { createCatalogStore, catalogFromEngine } from 'cracked-up/editor';

const catalog = createCatalogStore(catalogFromEngine(engine));
const drums = createEditor({ parent: drumsElement, doc: drumsCode, catalog });
const bass = createEditor({ parent: bassElement, doc: bassCode, catalog });

engine.buffers.on('ready', () => catalog.set(catalogFromEngine(engine)));
catalog.update({ ids: idsOfEveryTrack() });   // both editors follow

Before there is an engine

An audio context cannot start until someone clicks, and an editor is often on screen before that. catalogFromNodes makes the catalog from node definitions alone: the built-in types when called with nothing, or the list you give it. It creates no audio context, and its types are exactly what catalogFromEngine lists once the engine exists. 

import { catalogFromNodes } from 'cracked-up/editor';
import { builtinNodes } from 'cracked-up/nodes';

const catalog = createCatalogStore(catalogFromNodes());
// With your own types, and anything else a catalog holds:
catalog.set(catalogFromNodes([...builtinNodes, myMacro], { buses: ['drums'] }));

The same data without the editor is describeNodeTypes(definitions?) and describeNodeType(definition) from cracked-up: what engine.registry.list() and describe(type) report, read from the definitions.

With sandboxed scripts

When scripts run in a sandbox, the editor still lives in the page, and it behaves the same, because it only ever reads the catalog. catalogFromRemoteState makes one from what the link tells the sandbox, which includes node types that a script defined in the sandbox: 

import { catalogFromRemoteState } from 'cracked-up/editor';

editor.setCatalog(catalogFromRemoteState(link.state()));

A page with no engine at all, such as a collaborator's read-only view, can be sent the same data and build its catalog from that.

catalogFromRemoteState also lists the ids (with their node types), classes and buses of the scope's snapshot when the state has one. With an engine in the page, catalogFromScope(scope) gives the same names and the scope's sequences, to merge into a catalog after a script has run: catalogFromEngine(engine, catalogFromScope(scope)). catalogFromSnapshot(snapshot) reads the ids, classes and buses from a snapshot you already hold (scope.snapshot(), or one sent from another page). Each of these lists every id with its node type, which is what lets a function of your own complete the parameters of the node a selector names.

focus(), destroy() As named.

Other options: readOnly, lineNumbers, lineWrapping, ariaLabel, keymap (key bindings tried before the editor's own) and extensions (any CodeMirror extensions). editor.view is the CodeMirror view, for anything not covered here. Problems the host finds

showError is for the one error that stopped a script. For everything else an app notices, such as a selector that matches no node or a name that is not a sequence, setDiagnostics marks each place: a wavy underline, the line number in the colour of the worst problem on the line, and the message when the pointer rests on it. F8 and Shift-F8 move the cursor to the next and the previous problem and show its message; Escape hides it. 

editor.setDiagnostics([
  // by line, by line and column (the word there), or by position
  { line: 4, severity: 'warning', message: 'No node has the id "fliter".', source: 'controls' },
  { line: 9, column: 7, severity: 'error', message: 'There is no sequence called "stepz".' },
  { from: 120, to: 131, severity: 'info', message: 'This control is not used.' },
]);
editor.clearDiagnostics();

// Linking a list of your own to the code, both ways:
row.onclick = () => editor.reveal({ line: problem.line }, { flash: true, focus: true });
createEditor({ parent, onCursor: (cursor) => highlightControlDeclaredOn(cursor.line) });

Each call replaces the list before. In between, a problem follows its text as the user types, and one whose text is deleted goes with it; a problem that names a line the text has not got is left out. editor.diagnostics is the list as it stands, each with its from, to, line and column now. Each editor has its own list, and setValue with { history: 'reset' } empties it. The severities are 'error', 'warning' and 'info', coloured by --cu-error-text, --cu-warning-text and --cu-info-text. This is built from the CodeMirror packages listed above; @codemirror/lint is not needed.

Go to definition and the source panel

Cmd-click or F12 on a node type or a helper asks the editor for its definition. A type the script defines itself (define({ type: 'blip', ... })) is in the document, so the cursor goes there. For anything else a panel opens with its description, its parameters, and its TypeScript source with line numbers and a link to the file. A wrapper round a Web Audio node links to that node's page on MDN. A node type's name inside the source is a link to that type, and there is a back button. A type that came only as catalog data, such as one somebody else defined, shows what is known and says the source is not available.

The source of the built-in types and helpers is copied out of the library when it is built, into a file of its own that is loaded the first time the panel opens.

By default the panel is docked at the right of the editor. To put it somewhere of your own, pass an element, or make the panel yourself and share it between editors: 

import { createEditor, createSourcePanel } from 'cracked-up/editor';

const panel = createSourcePanel({ parent: document.querySelector('#sidebar'), catalog });
const editor = createEditor({ parent, catalog, sourcePanel: panel });

panel.show({ kind: 'type', name: 'tapedelay' });   // from a menu of your own, say

To draw the result yourself, take it from onDefinition. It is called first, with the kind, the name, the catalog's data for it, and for a type defined in the script where. Return true and the editor does nothing more: 

createEditor({
  parent,
  catalog,
  sourcePanel: false,
  onDefinition(target) {
    openMyInspector(target.kind, target.name, target.type ?? target.helper);
    return true;
  },
});

builtinSources(kind, name) gives the same source text the panel shows, and the sources option replaces where it comes from.

Helpers

Helpers are small functions for composing: rhythms, scales, random choices and number conversions. They make no sound themselves. They give you numbers and lists to use in your patterns and parameters. In the live demo and the sandboxed demo you call them by name. In your own project, import them from cracked-up/util (or from cracked-up/global, next to __). One group is for sounds rather than notes: waveform data, onsets and slice boundaries, described under Changing slices and drawing and editing a sound. 

__.transport.bpm = 100;
__().triangle({ id: 'lead', gate: 'closed' }).lowpass(2400).gain(0.25).to('main');
__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.3).to('main');

// A seed fixes the random choices: the same tune every time. Try another number.
const random = createRandom(4);

// A minor as MIDI notes: 57 is the A below middle C.
const notes = scales('minor').map((step) => 57 + step);
// Decide the tune once: eight notes picked from the scale.
const tune = fillArray(8, () => pick(notes, random));

// Five notes spread evenly over eight steps.
__.transport.sequence('lead', { steps: euclid(5, 8), step: '1/8' }, (ev) => {
  if (!ev.value) return;
  // One time in five, play the note an octave higher.
  const note = tune[ev.index] + (chance(0.2, random) ? 12 : 0);
  __('#lead').set({ frequency: pitchToFreq(note) }).trigger({ duration: ev.duration * 0.8 });
});

// A hat on every third sixteenth note, drifting against the tune.
const third = everyNth(3);
__.transport.sequence('hat', { steps: 'x', step: '1/16' }, () => {
  if (third()) __('#hat').trigger();
});

Patterns from patterns

The helpers under Changing patterns and Combining patterns take a pattern, as an array or a string, and return a new array. They can be nested, so one rhythm gives the others, and a sequence takes the result as its steps: 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().sampler({ id: 'snare', buffer: 'snare' }).gain(0.5).to('main');
__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.3).to('main');

const kick = euclid(3, 8);            // [1, 0, 0, 1, 0, 0, 1, 0]
const snare = rotate(kick, 2);        // the same rhythm from its third step: [0, 1, 0, 0, 1, 0, 1, 0]
const hat = invert(or(kick, snare));  // wherever neither of them plays
// Three bars of the kick, then one bar of it backwards.
const kicks = concat(repeat(kick, 3), reverse(kick));

__.transport.sequence('kick', { steps: kicks, step: '1/8' }, (ev) => {
  if (ev.value) __('#kick').trigger();
});
__.transport.sequence('snare', { steps: snare, step: '1/8' }, (ev) => {
  if (ev.value) __('#snare').trigger();
});
__.transport.sequence('hat', { steps: hat, step: '1/8' }, (ev) => {
  if (ev.value) __('#hat').trigger();
});

To change a pattern that is already playing, give the new one to sequence.update.

Random choices that repeat

Every helper that makes a random choice takes an optional last argument: where to get its random numbers. Leave it out and the choice is different on every run. Pass a seeded source and the choices come out the same every time, which is what you want when a piece should sound the same tomorrow, or when you render it to a file. createRandom(seed) makes one, and every engine has one of its own as engine.random. 

__().sine({ id: 'bell', gate: 'closed' }).gain(0.2).to('main');

// A random note of C minor on every eighth note, from the engine's own source.
__.transport.every('1/8', () => {
  const frequency = randomScale('minor', 5, 6, engine.random);
  __('#bell').set({ frequency }).trigger({ duration: 0.1 });
});

Every helper

The results shown are what the example gives. Where a helper has a second name, that is the name Cracked used for it, and it works here too.

Three things differ from Cracked on purpose. chance takes a probability from 0 to 1, not a percentage. shuffle returns a new list and leaves yours alone. pitchToFreq and freqToPitch do not round, so notes between the keys work.

euclid's third argument, rotate, starts the pattern that many steps later, which moves the hits earlier: euclid(3, 8) is [1, 0, 0, 1, 0, 0, 1, 0] and euclid(3, 8, 1) is [0, 0, 1, 0, 0, 1, 0, 1]. A negative number moves them later.
