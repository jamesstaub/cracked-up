When you need a sandbox

A cracked-up script is JavaScript. Run in your page, it can do anything your page can: read what is on screen, read storage, and call your server as the signed-in user. That is fine when the person who wrote the script is the person running it. It is not fine when the script came from someone else, which is what happens the moment two people edit one project: each person's browser runs the other person's code.

Situation Who wrote the script How to run it
Working alone on your own project You Directly, with scope.build. No sandbox needed
Opening a project someone shared with you Someone else In a sandbox
Editing a project together in real time Everyone in the session In a sandbox, for every participant

The rule is about where the code came from, not about who is looking at it. A project you wrote alone and later reopen is still yours. A project you forked from a stranger is not, until you have read it. An app should decide per project, and should treat "I am not sure" as "someone else".

The two ways of running a script are built to be interchangeable, so an app can use the direct way by default and switch to the sandbox when a project becomes shared, without its users rewriting anything.

The pieces

The audio engine always lives in your page. In sandboxed mode the script lives somewhere it can do no harm, and the two exchange plain data. 

your page                                   sandboxed frame (no origin)
---------                                   ---------------------------
Engine, audio graph, transport              the script
linkRemote(scope, ...)   <-- commands ---   createRemote(...)  gives the script __
                         --- events ---->   runs sequence callbacks
                         --- changes --->   keeps a copy of the scope's state
  • Writes are commands. Everything the script does (make a node, set a value, trigger a sampler) becomes a small object such as { op: 'trigger', target: '#kick', at: 12.5 }. The page applies it to one scope and nothing else.
  • Reads come from a copy. The sandbox holds a copy of the scope's nodes and values, so __('#filter').param('frequency').value answers at once, with no waiting.
  • Sequence callbacks run in the sandbox. The page's transport sends each step about 100 milliseconds before it sounds. The callback runs, and the commands it makes carry the step's exact time, so the result is as tight as it is without a sandbox. The round trip takes about a millisecond.

Both halves are in cracked-up/remote. The sandbox half (createRemote) contains no audio code and does not need a page: it also runs in a Worker.

One script, two ways to run it

Write scripts as a function of __, and give them a define function for their own node types. Then the same text runs either way: 

// A script, as your users write it.
define({
  type: 'blip',
  params: { pitch: { default: 660, min: 50, max: 4000,
                     drives: [{ select: '#tone', param: 'frequency' }] } },
  build(__) { __().sine({ id: 'tone', gate: 'closed' }).gain(0.2).to('out'); },
  trigger(__) { __('#tone').trigger({ duration: 0.05 }); },
});

__().blip({ id: 'blip' }).to('main');
__.transport.sequence('blips', { steps: 'x..x..x.' }, (ev) => {
  if (ev.value) __('#blip').trigger();
});

Running it directly, for code the user wrote:

import { defineMacro } from 'cracked-up';

function runDirect(scope, code) {
  const program = new Function('__', 'define', code);
  const define = (definition) => scope.engine.registry.register(defineMacro(definition));
  return scope.build((__) => program(__, define));
}

Running it sandboxed, for code from someone else (inside the frame):

function runSandboxed(remote, code) {
  const program = new Function('__', 'define', code);
  remote.build((__) => program(__, (definition) => remote.define(definition)));
}

Both rebuild in place: nodes the script still asks for keep sounding, and a script that throws leaves the previous version playing. A test in the library runs one script both ways and checks that the rendered audio is identical, sample for sample.

To keep scripts portable, do not hand direct-mode scripts anything a sandbox cannot offer. In particular do not pass them the engine. The differences table lists the few things that behave differently.

Setting up the sandbox

1. The frame

Use an iframe with sandbox="allow-scripts" and nothing else. Leaving out allow-same-origin is the point: the frame then has no origin, so it cannot read your page, your cookies, localStorage or IndexedDB, and requests it makes do not carry your users' session. 

<iframe id="guest" sandbox="allow-scripts" hidden></iframe>

A Worker on its own is not a sandbox. A Worker created by your page has your page's origin, so it can call your server as the user and read IndexedDB. Use a Worker only inside the sandboxed frame, if you want scripts off the frame's main thread.

2. The frame's page

Serve the frame's document with a content security policy that stops it from talking to the network. Without one, a script cannot steal anything from your page, but it can still make requests of its own. 

Content-Security-Policy: default-src 'none'; script-src 'self' 'unsafe-eval'; connect-src 'none'

'unsafe-eval' is there because the frame turns script text into a function. That is safe here because the frame has nothing worth stealing. Do not add it to your main page's policy. 

// guest.js, loaded by the frame's document
import { createRemote } from 'cracked-up/remote';

let remote = null;
const post = (message) => parent.postMessage(message, '*');

addEventListener('message', (event) => {
  if (event.source !== parent) return;
  const data = event.data;
  if (data.kind === 'init') {
    remote = createRemote({ ...data.state, send: (message) => post({ kind: 'remote', message }) });
    remote.on('error', (error) => post({ kind: 'error', message: error.message }));
  } else if (data.kind === 'host') {
    remote.receive(data.message);
  } else if (data.kind === 'run') {
    try {
      runSandboxed(remote, data.code);
      post({ kind: 'ok' });
    } catch (error) {
      post({ kind: 'error', message: String(error) });
    }
  }
});

post({ kind: 'ready' });

3. Your page

import { linkRemote } from 'cracked-up/remote';

const frame = document.querySelector('#guest');
const toFrame = (data) => frame.contentWindow.postMessage(data, '*');
let link = null;

addEventListener('message', (event) => {
  // The frame has no origin to check, so check the window the message came from.
  if (event.source !== frame.contentWindow) return;
  const data = event.data;
  if (data.kind === 'ready') {
    link = linkRemote(engine.scope('track-1'), {
      send: (message) => toFrame({ kind: 'host', message }),
      allow: (command) => command.op !== 'loadBuffer',
    });
    toFrame({ kind: 'init', state: link.state() });
    toFrame({ kind: 'run', code: scriptText });
  } else if (data.kind === 'remote') {
    link.receive(data.message);
  } else if (data.kind === 'error') {
    showError(data.message);
  }
});

// Set the address only after the listener exists, or "ready" can be missed.
frame.src = '/guest.html';

The target origin is '*' in both directions because a frame without an origin cannot be named. That is acceptable only because nothing secret is ever sent: the messages are commands and musical events. Never post a token, a user record or anything private to the frame.

Use one link and one scope per script. Call link.dispose() when the script goes away; it removes the script's sequences and node types. Disposing the scope removes its nodes.

Limiting what a script may do

The link enforces some limits by itself:

  • A script can only select, change and remove nodes in its own scope.
  • It can send audio to a bus of an outer scope, such as main, but cannot change that bus or take audio from it.
  • It cannot replace a node type it did not define.
  • A malformed message is reported and ignored. It never throws into your page.

Everything else is yours to decide in allow, which sees every command before it is applied and returns false to drop it: 

const MAX_NODES = 200;

const link = linkRemote(scope, {
  send,
  allow(command) {
    // The tempo belongs to the whole session, not to one track's script.
    if (command.op === 'transport') return false;
    // Scripts may only use audio the project already has.
    if (command.op === 'loadBuffer') return false;
    // A cap on how much one script can build.
    if (command.op === 'apply' && command.graph.nodes.length > MAX_NODES) return false;
    return true;
  },
});

A macro instance carries its inner graph in init.remote.graph, so a strict node cap should count those too. Commands for the inside of a macro arrive wrapped as { op: 'inside', node, commands }.

What to share between collaborators

cracked-up does not send anything over a network. Each participant runs their own engine and hears their own audio. What your app shares is the project: the text of the scripts and whatever settings your interface edits.

  • Share script text and project data, not commands. Commands are timed against one machine's audio clock and mean nothing on another. When a participant edits a script, send the new text; every browser runs it in its own sandbox.
  • Share graphs as data. scope.describe() returns a scope's nodes and connections as JSON, and scope.apply(graph) makes a scope match one, keeping what is unchanged. Use them for the parts of a project that an interface edits, such as adding an effect to a chain.
  • Share one tempo and one start. Tempo is a single value on the engine. To line participants up, share a start moment and have each browser start its transport for that moment. How closely they agree depends on your clock sharing; the library does not do it for you.
  • Expect randomness to differ. A script that calls Math.random() plays differently for each participant. Share a seed in the project if they should hear the same thing.

The link tells a script when something else changes its scope: a value set from a control arrives as a change, and nodes added or removed by the page arrive as a fresh copy of the scope. If the page and the script both change the structure in the same instant, the script's version wins, so let one side own the structure of a scope.

When a script misbehaves

  • It throws while building. remote.build rethrows, nothing is sent, and the previous version keeps playing. Show the error.
  • A sequence callback throws. The error goes to remote.on('error') with the code callback. The sequence carries on.
  • The page rejects something. A command that cannot be applied (an unknown bus, a method that does not exist) comes back to remote.on('error').
  • It loops forever. The frame stops answering and its sequences fall silent. Sound already scheduled keeps playing, because audio runs on its own thread. Whether your page stays responsive depends on the browser: some run a sandboxed frame in its own process, others share the page's thread with it. To be safe everywhere, have the frame run scripts in a Worker of its own (createRemote works there) and keep the frame itself idle, so it can end a stuck Worker. Detect a stuck script by sending a ping on a timer; if no answer comes back, end it, call link.dispose(), and start a new one.
  • It is slow. A callback that takes longer than the look-ahead (100 milliseconds by default) lands late. Its commands are applied on arrival. The sandboxed demo shows how to measure this.

Differences inside a sandbox

Thing Directly In a sandbox
Chains, selectors, setters, trigger, bypass, buses Yes The same
sequence, steps, every, at Yes The same. Callbacks run in the sandbox
An operation with no time, outside a callback Happens now Happens when it reaches the page, about a millisecond later
Defining a node type defineMacro, registered with the engine remote.define, same definition. A drive's scale must be data such as { multiply: 2 }, which also works directly
Reading values inside a macro from the page's own types Yes No. They can be set, not read
Transport position, start, stop Yes No. Events carry beat and bar
Tempo Read and set Read and set, unless allow refuses
Buffers engine.buffers remote.buffers.get(key) for duration and slices; load(url) if allow permits
Native audio nodes, defineNode, worklets Yes No. Register those in the page

Messages

Your app carries these between the two halves without needing to look inside. They are plain data and survive postMessage. The types are RemoteMessage and HostMessage.

Direction Message Meaning
Sandbox to page commands A batch of commands. At most one per turn of the event loop, plus one per sequence step
Sandbox to page define A node type the script defined, as data
Page to sandbox event A sequence step is coming up; run its callback
Page to sandbox call Someone called a method of a node type the script defined
Page to sandbox params, snapshot Values, or the scope's nodes, were changed by something other than the script
Page to sandbox transport, buffer Tempo or transport state changed; a buffer finished loading
Page to sandbox error Something the script sent could not be applied

Commands

The op values an allow function will see. The full shapes are the Command type.

Command What it does
apply Makes the scope's nodes and connections match a description
set, ramp, offset, cancel Change parameter values at a time
trigger, release, call, bypass Act on nodes at a time
connect, disconnect, dispose, bus Change connections, remove nodes, make or route a bus of the scope
inside Commands for the inside of one macro instance
sequence, once, setStep, restartSequence, clearSequence Schedule and edit the script's sequences and one-off callbacks
transport Sets tempo or swing for the whole engine. Consider refusing it
loadBuffer Makes the page fetch a URL. Consider refusing it, or checking the URL

Checklist

  • The frame has sandbox="allow-scripts" and not allow-same-origin.
  • The frame's document has a content security policy with connect-src 'none'.
  • The page checks event.source on every message from the frame.
  • Nothing private is ever posted to the frame.
  • The session token is not readable by scripts in the page (a cookie marked HttpOnly, not localStorage).
  • allow refuses loadBuffer and transport unless you mean to permit them.
  • There is a cap on nodes per script, and a ping to catch a frame that has stopped.
  • Any project whose scripts the current user did not write runs sandboxed.
