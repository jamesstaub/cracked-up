Introduction

cracked-up is a JavaScript library for making sound and music in the browser by writing code. You describe a sound as a chain of simple parts, such as an oscillator into a filter into a volume control, and a musical clock plays your patterns in time. It is meant for live coding, and for apps that let people write small music scripts. 

__().saw({ id: 'bass', gate: 'closed' }).lowpass(700).gain(0.3).to('main');

__.transport.sequence('bass', { steps: [55, 0, 55, 82.4], step: '1/8' }, (ev) => {
  if (ev.value) __('#bass').set({ frequency: ev.value }).trigger({ duration: 0.15 });
});

Every example on this page has a Try it link that opens it in the live demo, where you can change it while it plays.

Where it comes from

cracked-up is based on I Dropped My Phone The Screen Cracked by Bill Orcutt, called Cracked for short on this page. Cracked had the idea this library keeps: one object, __, with which you chain audio nodes together and later find them again with selectors like the ones in CSS, such as __('#bass') or __('lowpass').

cracked-up is a rewrite, not a new version of Cracked. It was written from scratch in TypeScript, and many names and rules changed, so code written for Cracked will not run here without changes. A few of the differences:

In Cracked Here
__().sine().dac() __().sine().to('main'). Chains end at a named bus
A later line such as __.lowpass() carries on the last chain A chain is a value. You carry on from that value, or select nodes by name
.attr({ frequency: 200 }) .set({ frequency: 200 }) or .frequency(200). See Changing parameters
.start(), .stop() .trigger(), .release(). See Starting and stopping sounds
__.loop(...) and .bind('step', ...) __.transport.sequence(...). See Sequencing

Cracked is released under the MIT licence, copyright 2014 Bill Orcutt. cracked-up is released under the MIT licence too. Its licence file keeps Bill Orcutt's copyright line and adds one for the new code (2026, James Staub).

Why a rewrite, and what is new

Cracked keeps everything in one shared place: one set of nodes for the whole page, and a memory of "the last node made". That is quick to type, but two pieces of code on the same page can disturb each other, and timing depends on how busy the page is. The rewrite set out to remove those limits and keep the feel. What that gave:

  • Nothing shared behind your back. Sound lives in an engine that you create, and a page can have more than one. An engine can be divided into scopes, for example one for each track. Code given one track's scope cannot find or change the nodes of another track.
  • Selections that do not get in each other's way. __('lowpass') gives back a selection you can keep in a variable and use again. Using one selection never changes what another one points at. See Selecting nodes.
  • Tight timing. A transport keeps the tempo and schedules each step slightly ahead of time on the audio clock, so notes land on the exact sample even when the page is briefly busy. It runs any number of sequences at once, with different lengths and step sizes (polyrhythm), swing, and tempo changes. See Sequencing.
  • Parameters that describe themselves. Every parameter knows its range, unit, default value and what it does. The node reference on this page is made from that information, and an app can use it to draw the right knob for each parameter.
  • Macros. Several nodes can be wrapped up as one new node type with its own parameters. The built-in polysynth is made this way.
  • Changing code while it plays. Run changed code again and only what changed is rebuilt. Everything else keeps sounding, and sequences stay in time. See Re-running code.
  • Offline rendering. The same code can be rendered to audio without playing it, faster than real time, and it comes out the same on every run. See Stems and files. The library's own tests work this way: they render sound in real browsers and check the result.
  • Modern audio processing. Where Cracked ran custom sound code with ScriptProcessor, an older browser feature that shares a thread with the page and can glitch, cracked-up uses AudioWorklet, which runs with the rest of the audio. The bitcrusher, recorder and looper are built on it.
  • Recording and looping. A recorder and a looper that start and stop on the exact sample, live input, and separate files for each part of a mix (stems). See Recording, looping and live input.
  • MIDI. Play a synth from a keyboard, map a controller to a parameter, send notes out, and keep time with other gear in either direction. See MIDI.
  • Running other people's scripts safely. A script can run in a sandbox, a closed-off part of the browser where it cannot read your page, and still play in time. This is what makes sharing scripts between collaborators possible. See Running scripts in a sandbox and the guide Running other people's scripts.
  • Types. The library is written in TypeScript. An editor can complete node names and options as you type, and point out a misspelled one before you run it.
  • The composing helpers are still here. Cracked's small functions for scales, random choices and number conversions are listed under Helpers.

Where it stands

cracked-up is pre-alpha. It is not published to npm, and names and behaviour may still change. Releases are numbered by semantic versioning, starting at 0.1.0; while the number starts with 0, a change that breaks existing code raises the middle number. The repository's CHANGELOG.md lists what changed in each. What this page describes is implemented, and the tests run in Chromium, Firefox and WebKit. Known limits:

  • MIDI is tested with pretend devices only. Its timing has not been measured against real hardware.
  • Safari has no Web MIDI, so MIDI does not work there.
  • Recording from a live microphone is tested in Chromium only.
  • Recordings are kept in memory without compression. There is no mode for very long takes yet.
  • MIDI is not available to scripts running in a sandbox.

The basics

You build sound by chaining nodes. A node makes sound (an oscillator, a sampler) or changes it (a filter, a gain). __() starts a chain; each method adds a node and connects the previous one to it. 

__().saw(110).lowpass(800).gain(0.3).to('main');

That is a sawtooth oscillator at 110 Hz, into a low-pass filter at 800 Hz, into a gain of 0.3, into the output. A chain you do not send anywhere makes no sound.

Give a node an id when you want to reach it later. Pass options as an object; a bare value sets the node's main parameter, so lowpass(800) is short for lowpass({ frequency: 800 }). 

__().saw({ id: 'bass', frequency: 55 })
  .lowpass({ id: 'filter', frequency: 400, q: 8 })
  .gain(0.3)
  .to('main');

Where sound goes: main

main is the engine's output. It is a bus: a named point where any number of chains are mixed together. The engine creates main for you and connects it to your speakers. It is the only bus that exists until you make another. You never define it yourself, and it cannot be removed.

main is stereo. A mono sound sent to it is heard equally on both sides; use a panner before it to place a sound left or right.

In the original Cracked library every chain ended with its own .dac() node. Here every chain ends at the one shared main, which gives a single place to set the overall level, and later to meter or record everything. 

__().sine(220).gain(0.2).to('main');
__.bus('main').gain.set(0.5); // overall level

You can make more buses to group sounds, for example a shared effect. A new bus feeds main until you route it somewhere else. 

__.bus('drums').gain.set(0.8);
__().sampler({ id: 'kick', buffer: 'kick' }).to('drums');
__().sampler({ id: 'hat', buffer: 'hat' }).to('drums');
__.transport.every('1/4', () => __('sampler').trigger());

Sending to a bus that does not exist is an error, so a mistyped name is caught at once.

to, connect and modulate

All three make a connection from the end of a chain. They differ in what they connect to.

Method Connects to A string means
.to('main') A bus The bus's name
.connect('#filter') The input of one or more existing nodes A selector that finds the nodes
.modulate('#filter', 'frequency') A parameter of existing nodes, so the signal moves that parameter A selector that finds the nodes

So .to('main') and .connect(engine.bus('main')) do the same thing. to exists because ending a chain at a bus is the common case, and because a string there is a bus name, while a string given to connect is a selector. 

// Two oscillators into one filter.
__().lowpass({ id: 'filter', frequency: 600 }).gain(0.2).to('main');
__().saw(110).connect('#filter');
__().square(165).connect('#filter');

// A slow sine moves the filter's cutoff by +/- 300 Hz.
__().sine(0.5).gain(300).modulate('#filter', 'frequency');

When something modulates a parameter, its signal is added to the parameter's own value. An oscillator swings between -1 and 1, so a gain after it sets how far the parameter moves.

Selecting nodes

__('selector') finds nodes you have already made and returns them as a selection. Whatever you call on a selection applies to every node in it.

Selector Finds
sampler Every node of that type
#kick The node with that id
.drums, .drums.loud Nodes with that class, or with all of several classes
[role=send], [solo] Nodes with a tag of that value, or with that tag at all
sine, saw Either
sampler:not(.muted) Samplers without the class
gain:nth(1) The second gain, counting from 0 in the order they were made
* Everything 
__().sampler({ id: 'kick', buffer: 'kick', class: 'drums' }).to('main');
__().sampler({ id: 'hat', buffer: 'hat', class: 'drums' }).to('main');

__.transport.sequence('beat', { steps: [1, 2], step: '1/4' }, (ev) => {
  __(ev.value === 1 ? '#kick' : '#hat').trigger();
});

Classes and tags are set when a node is made: { class: 'drums loud', tags: { role: 'send' } }.

Changing parameters

Every node has parameters, listed in the reference below. Each one has a base value: the value you set, and the one a slider would show.

Call Does
.set({ frequency: 800, q: 4 }) Sets base values
.frequency(800) The same, for one parameter. There is a setter for every parameter name
.ramp('frequency', 2000, { duration: 2 }) Glides the base value to a target over a number of seconds
.offset('frequency', 500, { duration: 0.1 }) Adds an amount on top of the base value for a while, then returns to it
.param('frequency').value Reads the base value 
__().saw(110).lowpass({ id: 'filter', frequency: 200, q: 6 }).gain(0.2).to('main');
__('#filter').ramp('frequency', 3000, { duration: 4 });

The one exception to the setter rule is a parameter called release (on the compressor): .release() already means "release the note", so that parameter is set with .set({ release: 0.2 }).

The minimum and maximum in the reference are the range a control would cover. They are not limits: you can set a gain of 300 when it is scaling a modulation.

Starting and stopping sounds

.trigger() starts a sound and .release() ends it. What that means depends on the node.

A sampler plays its buffer once per trigger. Each trigger is a new voice, so you never need to stop or rewind it before the next hit. Options given to trigger apply to that hit only. 

__().sampler({ id: 'hat', buffer: 'hat' }).to('main');
__.transport.sequence('hat', { steps: 4, step: '1/8' }, (ev) => {
  __('#hat').trigger({ speed: 1 + ev.index * 0.2, velocity: 0.6 });
});

An oscillator runs from the moment it is made and is heard straight away, as a drone. release() closes its gate and trigger() opens it. To make one that is silent until triggered, create it with gate: 'closed'. 

__().square({ id: 'blip', frequency: 660, gate: 'closed' }).gain(0.15).to('main');
__.transport.every('1/4', () => __('#blip').trigger({ duration: 0.08 }));

Samplers and where their audio comes from

A sampler plays a buffer: a piece of recorded sound held in memory. The engine keeps a store of named buffers, engine.buffers, so the same sound is decoded once and shared by every sampler that uses it.

A sampler's buffer option accepts three things:

You pass What happens
A name already in the store, such as 'kick' That buffer is used
Any other string It is treated as a URL: the file is fetched, decoded, and stored under that URL. The sampler is silent until loading finishes. The server must allow requests from this page.
An AudioBuffer you made or decoded yourself It is used directly

In the live demo, 'kick', 'snare' and 'hat' are not files. The demo page generates them with a few lines of maths when audio starts and adds them to the store by name: 

engine.buffers.add('kick', audioBuffer);

A buffer can be cut into slices by giving it boundaries in seconds. A trigger can then play one slice by number. 

const kit = engine.buffers.get('snare');
kit.slices = [0, 0.03, 0.1, 0.25];
__().sampler({ id: 's', buffer: 'snare' }).to('main');
__.transport.sequence('slices', { steps: [0, 1, 2], step: '1/8' }, (ev) => {
  __('#s').trigger({ slice: ev.value });
});

Slicing a drum break

A break is a few bars of a drummer playing alone. Cut into slices, it becomes a drum kit that keeps the feel of the original playing: you can play the slices in a new order, repeat them, reverse them and change their pitch. Jungle and breakcore are built on this.

The live demo loads one break under the name 'break'. It is Crunchy Drum Break 2 [128bpm] by deadrobotmusic, shared on Freesound under the Creative Commons 0 licence. The demo page fetches it from Freesound when audio starts. If that fails, the page says so, samplers that play 'break' are silent, and everything else works.

The break is 8 bars long at 128 beats per minute, which is 15 seconds. The demo page cuts it into 128 slices, one for every sixteenth note: slice 0 is the first sixteenth of bar 1, slice 16 is the first sixteenth of bar 2, and so on. In every bar the kick drum is on sixteenths 0, 7 and 14, the snare is on 4 and 10, and there is a hi-hat on the other even ones. The odd ones mostly hold the tail of the hit before.

Staying in time

trigger({ slice: n }) plays slice n. A slice of this break lasts one sixteenth note at 128 bpm. To make it last one sixteenth note at your tempo, play it faster or slower by the ratio of the two tempos: speed = your bpm / 128. Then the break follows the transport at any tempo. Like a record, a sample played faster also sounds higher. 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');

// The break was played at 128 bpm. At this speed one slice lasts exactly one step.
const speed = __.transport.bpm / 128;

// 128 steps, one for each slice: the whole break, in order, at your tempo.
__.transport.sequence('break', { steps: 128 }, (ev) => {
  __('#break').trigger({ slice: ev.index, speed });
});

Change the bpm and the break stays in time. A slice number past the last slice wraps round to the start.

Setting the grid

The slices of a buffer are a list of boundaries in seconds. You can replace the list at any time. This cuts the same break into 64 eighth notes instead. It is not run from here, because it would change the grid for every other example until you reload the demo: 

const sound = engine.buffers.get('break');
// 64 slices need 65 boundaries, spread evenly over the 15 seconds.
sound.slices = fillArray(65, (i) => (i * 15) / 64);

An even grid works for this break because it starts exactly on its first hit, ends exactly on a bar line, and was played to a steady beat. For a break that does not, start the list later than 0, or put each boundary where a hit begins.

A new order

Give the sequence a pattern of slice numbers and the drummer plays a beat that was never recorded: 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');
const speed = __.transport.bpm / 128;

// Which sixteenth of the first bar to play on each step.
// 0 is a kick, 4 and 10 are snares, 12 is a hat.
const order = [0, 0, 4, 12, 7, 4, 12, 0, 10, 14, 4, 4, 0, 7, 4, 10];

__.transport.sequence('break', { steps: order }, (ev) => {
  __('#break').trigger({ slice: ev.value, speed });
});

Rolls, reverses and pitch

A roll is one hit repeated very fast. ev.at(0.5) is the moment halfway through a step, so several triggers at different fractions of the step make a roll. duration cuts each hit short, reverse: true plays a slice backwards, and multiplying speed changes the pitch: twice the speed is an octave higher and lasts half as long. 

__.transport.bpm = 150;
__().sampler({ id: 'break', buffer: 'break' }).to('main');
const speed = __.transport.bpm / 128;

__.transport.sequence('break', { steps: 16 }, (ev) => {
  const hit = __('#break');
  if (ev.bar % 2 === 1 && ev.index >= 12) {
    // A roll: the snare four times inside each of the last four steps, getting higher.
    for (let i = 0; i < 4; i++) {
      hit.trigger({
        slice: 4,
        at: ev.at(i / 4),
        speed: speed * (1 + (ev.index - 12) / 4),
        duration: ev.duration / 4,
      });
    }
  } else if (ev.index === 6) {
    // Backwards: the sound swells up to the next step.
    hit.trigger({ slice: 4, speed, reverse: true });
  } else if (ev.index === 9) {
    // Twice as fast: an octave higher and half as long.
    hit.trigger({ slice: ev.index, speed: speed * 2 });
  } else {
    hit.trigger({ slice: ev.index, speed });
  }
});

All together: breakcore

Breakcore is fast and restless: the break is cut up, reordered, stuttered and pitched, and it rarely plays the same bar twice. This example has a four-bar phrase. Bar 1 is the break in order with a few tricks. Bar 2 is a new order. Bar 3 is half-time, dark and low. Bar 4 is double-time and ends in a snare roll. A sub bass plays under every kick drum, and now and then a snare is thrown into an echo. The random choices come from a seed, so the phrase is the same each time round. Change the seed, the tempo or a pattern and listen. 

// Breakcore from one drum break: sliced, shuffled, rolled and pitched.
// The sound is "Crunchy Drum Break 2 [128bpm]" by deadrobotmusic (Creative Commons 0):
// https://freesound.org/people/deadrobotmusic/sounds/629052/

__.transport.bpm = 172;

// The break is 8 bars at 128 bpm. The demo page has cut it into 128 slices,
// one for every sixteenth note. Played at this speed a slice lasts exactly one step, so the
// break stays in time at any tempo. Change the bpm above and listen.
const speed = __.transport.bpm / 128;

// --- The sounds ---------------------------------------------------------------
// The drum bus is made gritty and goes through a filter. to(null) means the bus
// is heard only through this chain.
__.bus('drums').to(null).chain()
  .bitcrusher({ bits: 10, rate: 0.6 })
  .lowpass({ id: 'tone', frequency: 14000 })
  .to('main');
__().sampler({ id: 'break', buffer: 'break' }).to('drums');

// A second player of the same break, heard only as echoes: a "delay throw".
__().sampler({ id: 'throw', buffer: 'break' })
  .highpass(600)
  .delay({ time: __.transport.seconds('1/8d'), feedback: 0.6, mix: 1 })
  .gain(0.5)
  .to('main');

// A sub bass. It plays under every kick drum, wherever the kick ends up.
__().sine({ id: 'sub', gate: 'closed' }).overdrive(0.5).gain(0.5).to('main');
const bassNotes = [43.65, 43.65, 51.91, 38.89]; // one per bar: F, F, G sharp, D sharp

// --- The plan -----------------------------------------------------------------
// In each bar of the break the kick is on sixteenths 0, 7 and 14, the snare on 4 and 10.
const kicks = [0, 7, 14];
const inOrder = fillArray(16, (i) => i);
const chopped = [0, 0, 4, 7, 7, 4, 2, 0, 10, 14, 4, 4, 0, 7, 4, 10];

// A seed makes the random choices come out the same on every run. Try another number.
const random = createRandom(5);
// The eight eighth notes of a bar, in a random order.
const jumbled = shuffle([0, 2, 4, 6, 8, 10, 12, 14], random).flatMap((s) => [s, s + 1]);

// The phrase is four bars long. Each bar has a pattern and a feel:
// 1 is normal, 0.5 is half-time, 2 is double-time.
const patterns = [inOrder, chopped, inOrder, jumbled];
const feels = [1, 1, 0.5, 2];
// A trick for each step, chosen once, so the phrase has a shape that comes back.
// The first step of a bar is always left alone.
const tricks = fillArray(64, (i) =>
  i % 16 > 0 && chance(0.3, random) ? pick(['roll', 'reverse', 'high', 'gate', 'rest'], random) : 'plain',
);

// Plays one slice. If it holds a kick drum, the sub bass plays with it.
const hit = (slice, at, options) => {
  __('#break').trigger({ slice, at, speed, ...options });
  if (kicks.includes(slice % 16)) __('#sub').trigger({ at, duration: 0.14 });
};

// --- The break ----------------------------------------------------------------
__.transport.sequence('break', { steps: 16 }, (ev) => {
  const bar = ev.bar % 4;
  const step = ev.index;
  const trick = tricks[bar * 16 + step];
  // Use the matching bar of the break, so the drummer's own changes come through.
  const from = 16 * (ev.bar % 8);
  const slice = from + patterns[bar][step];

  if (step === 0) {
    __('#sub').set({ frequency: bassNotes[bar] });
    // The half-time bar is darker.
    __('#tone').set({ frequency: feels[bar] === 0.5 ? 2500 : 14000 });
  }

  if (bar === 3 && step >= 8) {
    // The fill that ends the phrase: a snare roll that gets faster and higher.
    const count = [2, 2, 3, 3, 4, 4, 6, 8][step - 8];
    const rollSpeed = speed * (1 + (step - 8) / 8);
    for (let i = 0; i < count; i++) {
      hit(from + 4, ev.at(i / count), { speed: rollSpeed, duration: ev.duration / count });
    }
  } else if (feels[bar] === 0.5) {
    // Half-time: on every second step, one slice at half speed. It lasts two steps
    // and sounds an octave lower.
    if (step % 2 === 0) hit(from + patterns[bar][step / 2], ev.time, { speed: speed / 2 });
  } else if (feels[bar] === 2) {
    // Double-time: two slices in every step, at twice the speed.
    hit(from + patterns[bar][(step * 2) % 16], ev.time, { speed: speed * 2 });
    hit(from + patterns[bar][(step * 2 + 1) % 16], ev.at(0.5), { speed: speed * 2 });
  } else if (trick === 'roll') {
    // A stutter: the same slice three times inside one step.
    for (let i = 0; i < 3; i++) hit(slice, ev.at(i / 3), { duration: ev.duration / 3 });
  } else if (trick === 'reverse') hit(slice, ev.time, { reverse: true });
  else if (trick === 'high') hit(slice, ev.time, { speed: speed * 2 });
  else if (trick === 'gate') hit(slice, ev.time, { duration: ev.duration * 0.3 });
  else if (trick !== 'rest') hit(slice, ev.time, {});

  // Throw the second snare of bars 2 and 4 into the echo.
  if (bar % 2 === 1 && step === 10) __('#throw').trigger({ slice: from + 4, speed });
});

Time

Most calls take an optional at: the moment the change should happen, in seconds on the audio clock (engine.context.currentTime). Leave it out and the change happens now. Scheduled changes land on the exact sample. 

const now = engine.context.currentTime;
__().sine({ id: 'tone', frequency: 220 }).gain(0.2).to('main');
__('#tone').set({ frequency: 330 }, { at: now + 1 });
__('#tone').set({ frequency: 440 }, { at: now + 2 });

Inside a sequence callback you rarely need at: anything you do there happens at the step's own time. See the next section.

Sequencing: the transport

The transport keeps musical time: a tempo and a position in beats. A sequence is a repeating pattern of steps on it. For each step, your function is called with an event describing that step. You reach it as __.transport. 

__.transport.bpm = 120;
__().sampler({ id: 'kick', buffer: 'kick' }).to('main');

__.transport.sequence('kick', { steps: 'x...x...x..x..x.' }, (ev) => {
  if (ev.value) __('#kick').trigger();
});

steps is the pattern, as an array of numbers or a string. In a string, x means 1 and . means 0, so 'x..x' is the same as [1, 0, 0, 1]. A value of 0 is a rest; your function is still called, which is why the example checks ev.value. Values can be any number, so a step can say which sample to play or what pitch to use.

Option Meaning
steps The pattern. A plain number, such as 5, means that many steps, all with value 1
step How long one step lasts: '1/16' (the default), '1/8', '1/8t' for a triplet, '1/8d' for dotted, or a number of beats
span Use instead of step to spread the steps evenly over a length: { steps: 5, span: '1 bar' } is five in a bar
swing 0.5 is straight. Above 0.5 delays every second step
offset Shifts the whole pattern later by a length
probability Chance, from 0 to 1, that each hit is played
rests false stops your function being called for rests

The event your function receives:

Field Meaning
ev.value The step's value from the pattern
ev.index Which step of the pattern this is, counting from 0
ev.cycle How many times the pattern has repeated
ev.time The exact moment the step sounds, on the audio clock
ev.duration How long the step lasts, in seconds
ev.at(0.5) A moment part-way through the step: 0.5 is halfway. For extra hits between steps
ev.beat, ev.bar Where the step is in the music

Your function runs a fraction of a second before its step is heard, and whatever it does is timed to land exactly on the step. That is why timing stays tight even when the page is busy. It also means a slow function does not make the music late.

Every sequence follows the same transport, so sequences with different step lengths stay locked together. That makes polyrhythms a matter of choosing lengths: 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.5).to('main');

// Four against five in the same bar.
__.transport.sequence('four', { steps: 4, span: '1 bar' }, () => __('#kick').trigger());
__.transport.sequence('five', { steps: 5, span: '1 bar' }, () => __('#hat').trigger());
__().sampler({ id: 'hat', buffer: 'hat' }).to('main');

// A swung pattern with a quick double hit on the last step.
__.transport.sequence('hat', { steps: 'x.xx', step: '1/8', swing: 0.6 }, (ev) => {
  if (!ev.value) return;
  __('#hat').trigger();
  if (ev.index === 3) __('#hat').trigger({ at: ev.at(0.5), velocity: 0.5 });
});

Giving a sequence a name lets you change it: calling __.transport.sequence again with the same name replaces the old one without losing its place. __.transport.every('1/4', fn) calls a function at a regular interval with no pattern, and __.transport.at('2 bars', fn) calls one once.

Recording, looping and live input

A recorder sits in a chain, passes the sound through, and records it when triggered. The recording goes into the buffer store under a key, where a sampler can play it. Starting and stopping are exact to the sample, so recorders started together make recordings that line up. 

__().sampler({ id: 'hit', buffer: 'snare' }).recorder({ id: 'rec', into: 'take' }).gain(0.5).to('main');
__().sampler({ id: 'again', buffer: 'take', speed: 0.5 }).to('main');
__.transport.every('1/4', () => __('#hit').trigger());

// Every two bars, record half a bar. Every bar, play the latest take at half speed.
__.transport.every('2 bars', () => __('#rec').trigger({ duration: __.transport.seconds('1/2') }));
__.transport.every('1 bar', () => __('#again').trigger());

Make the recorder before the sampler that plays its key, so the key exists. Each new take replaces the last one under that key; give trigger a key to keep takes apart.

A looper records a loop of a fixed length and plays it round and round. Each later trigger() adds a layer; call('undo') removes the newest and call('clear') empties it. Start the first layer on a bar line and it stays on the bar: the loop is timed against the audio clock itself, so it does not drift, though it will not follow a later change of tempo. 

__().sampler({ id: 'hit', buffer: 'kick' }).looper({ id: 'loop', length: '1 bar' }).gain(0.6).to('main');

// The kick plays for one bar in every four. The looper records that bar and repeats it.
__.transport.sequence('feed', { steps: 'x..x..x.' + '.'.repeat(24), step: '1/8' }, (ev) => {
  if (ev.value) __('#hit').trigger();
});
__.transport.every('4 bars', () => {
  __('#loop').call('clear').trigger();
});

Recording any part of your sound

Recorders and loopers take whatever is connected to them, not just a microphone. The usual way to choose what gets captured is a bus: send any number of chains to it, and continue from the bus into the recorder or looper. Nothing is captured until you trigger() the recorder or looper, so a complete example needs three things: the routing, something playing, and a trigger. 

// ROUTING. Anything sent to 'loop-in' can be looped. to(null) stops the bus feeding the
// output by itself, so its one way out is through the looper. Without it you would hear
// everything twice.
__.bus('loop-in').to(null).chain().looper({ id: 'loop', length: '1 bar' }).to('main');

// SOMETHING PLAYING. Two different chains feed the bus: a synth, and a sampler through a filter.
__().polysynth({ id: 'keys', release: 0.2 }).gain(0.5).to('loop-in');
__().sampler({ id: 'hat', buffer: 'hat' }).highpass(5000).gain(0.4).to('loop-in');

// They are only played in the first bar of every four.
__.transport.sequence('keys', { steps: [60, 0, 67, 0, 63, 0, 70, 0], step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 === 0) __('#keys').trigger({ pitch: ev.value, duration: 0.15 });
});
__.transport.sequence('hats', { steps: 'x.xx', step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 === 0) __('#hat').trigger();
});

// A TRIGGER. On that first bar, empty the looper and record. For the other three bars
// nothing is being played: what you hear is the loop.
__.transport.every('4 bars', () => __('#loop').call('clear').trigger());

A recorder is routed the same way. Chained from a bus without to(null) it listens in while the bus plays on as normal, and from main it hears everything: 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().sampler({ id: 'snare', buffer: 'snare' }).gain(0.6).to('main');
__.transport.sequence('kick', { steps: 'x..x..x.', step: '1/8' }, (ev) => {
  if (ev.value && ev.bar % 4 < 2) __('#kick').trigger();
});
__.transport.sequence('snare', { steps: [0, 1], step: '1/4' }, (ev) => {
  if (ev.value && ev.bar % 4 < 2) __('#snare').trigger();
});

// A recorder on the whole mix, and a sampler that plays what it recorded.
__.bus('main').chain().recorder({ id: 'tape', into: 'mix-bar' });
__().sampler({ id: 'tape-play', buffer: 'mix-bar', speed: 0.5 }).to('main');

// The drums play for two bars in every four. Record the second of them, exactly one bar...
__.transport.every('4 bars', () => {
  __('#tape').trigger({ duration: __.transport.seconds('1 bar') });
}, { offset: '1 bar' });
// ...and play it at half speed over the two silent bars.
__.transport.every('4 bars', () => __('#tape-play').trigger(), { offset: '2 bars' });

Recordings and loops stay in time if you start them on a bar line and measure them in bars: start from a transport callback (every('4 bars', ...)), give a recorder duration: __.transport.seconds('1 bar'), and give a looper a length such as '2 bars'. The starter code in the live demo does both.

Layers added to a looper after the first are recorded at its overdub level, 0.7 unless you change it, so that layers stacked on each other do not add up to distortion. Set overdub: 1 to record every layer at full level.

input is a microphone or audio interface. The browser asks for permission the first time. Sound from an input arrives late, by the time it takes to get through the audio hardware and back. Tell a recorder or looper how late with its latency parameter and it shifts what it records to match, so an overdub lines up with what the player heard. A reasonable starting value is engine.context.outputLatency plus the input's own delay; let people adjust it by ear. 

__().input().looper({ id: 'loop', length: '2 bars', latency: 0.02 }).to('main');

Stems and files

To render a piece to separate files, build it on an offline engine, put a recorder on each bus you want a stem of, and render. A take still open when the render ends is finished there, so every stem is as long as the mix. 

import { createEngine } from 'cracked-up';
import { encodeWav } from 'cracked-up/util';

const context = new OfflineAudioContext(2, 48000 * 60, 48000);
const engine = await createEngine({ context });

const drums = engine.scope('drums');
drums.bus('out').chain().recorder({ id: 'stem', into: 'stem:drums' });
// ...build the drums, sending them to 'out', and the other tracks the same way...

engine.select('recorder').trigger({ at: 0 });
engine.transport.start();
const mix = await engine.render();
const drumStem = await engine.buffers.get('stem:drums').ready;

const file = new Blob([encodeWav(mix, { bitDepth: 24 })], { type: 'audio/wav' });

encodeWav writes 16-bit, 24-bit or 32-bit floating-point files from any recording or render.

MIDI

MIDI lives in its own part of the library, cracked-up/midi, and belongs to the page rather than to a script: the page asks for access once and decides what to do with it. It needs a browser with Web MIDI (Chrome, Edge, Firefox; not Safari), and requestMidi fails with a clear message where there is none.

The live demo has done this for you: a midi object is there by that name, and the browser asks you to allow MIDI the first time your code uses it. Each run of the code replaces the listeners and bindings of the run before, and a follow or sendClock that has not changed is left running, so editing the code does not restart the sync. With a keyboard plugged in, this plays a synth from it: 

__().polysynth({ id: 'keys' }).to('main');
midi.play(() => __('#keys'));

// Every note that arrives, whatever it is used for.
midi.on('noteon', (note) => console.log(note.note, note.velocity));

The examples below are written for a page's own code, where midi comes from requestMidi. They work in the demo too with two changes: use __ where they say engine, and where one says await, use .then(...), because a demo script cannot wait. 

import { requestMidi } from 'cracked-up/midi';

const midi = await requestMidi(engine);
midi.inputs;                       // [{ id, name, manufacturer }, ...]
midi.on('devices', () => { /* something was plugged in or removed */ });

Playing and controlling

// Notes from a keyboard play a synth: note-on triggers the pitch, note-off releases it.
engine.chain().polysynth({ id: 'keys' }).to('main');
midi.play(() => engine.select('#keys'));

// Any message, on any channel, with as many listeners as you like.
midi.on('noteon', (note) => console.log(note.note, note.velocity, note.channel), { channel: 10 });
midi.on('pitchbend', (bend) => engine.select('#keys').set({ detune: bend.value * 200 }));

// Tie a knob to a parameter. The knob's travel covers the parameter's control range.
midi.bind({ controller: 74 }, () => engine.select('#filter').param('frequency'));

// Or let the person choose the knob: this waits for the next one they move.
const binding = await midi.learn(() => engine.select('#filter').param('frequency'));
binding.remove();

Give bind and learn a function that finds the parameter, as above, rather than the parameter itself. Then the knob keeps working after code is re-run and the node behind it has been replaced.

Sending notes

const out = midi.output('My Synth');   // by name or id; the first output if you give none
out.channel = 2;

engine.transport.sequence('bass', { steps: [36, 0, 36, 43], step: '1/8' }, (ev) => {
  // No time given: inside a sequence it lands exactly on the step.
  if (ev.value) out.note(ev.value, { duration: ev.duration * 0.8, velocity: 0.9 });
});
out.cc(1, 0.5);
out.pitchBend(-1);

Keeping time with other gear

// Other gear follows this page: clock pulses, Start, Stop, and where to continue from.
const stopSending = midi.sendClock('Drum Machine');

// This page follows other gear: its Start and Stop, its tempo, its position.
const follow = midi.follow('Drum Machine');
follow.bpm;      // the tempo measured from the incoming clock
follow.error;    // how far the transport is from the clock right now, in seconds
follow.stop();   // go back to the transport's own tempo

While following, setting transport.bpm does nothing, so code that sets a tempo can be re-run without fighting the clock. Timing is matched to what is heard, not to what has been computed: notes and clock sent out are delayed by the audio output's latency, so a drum machine and the page's own sound line up at the speakers.

How tight is it? With a pretend clock whose pulses each arrive up to 1.5 milliseconds early or late, the transport stays within 2 milliseconds of it at 70, 120 and 174 bpm, and comes back onto the clock after a tempo change. That has been measured with simulated and in-browser clocks only. It has not yet been measured against real hardware, where the MIDI interface and driver add their own delay and unevenness.

Code that is run again and again

A script that is re-run on every edit would add its listeners again each time, and would start following the clock afresh, which takes about a beat to settle. Run it through midi.build and its calls replace the ones the last run made. Listeners, bindings and play are swapped. A follow or sendClock with the same arguments as one already running is kept, with the tempo it has measured. Calls the new run no longer makes are stopped, and if the run throws, nothing changes. This is what the live demo does. 

// Each time the script changes:
midi.build((midi) => runScript(midi));

// Or in two steps, when you only know later whether the run worked:
const session = midi.session();
runScript(session.midi);
if (ok) session.commit();
else session.rollback();

Every MIDI method

midi. below stands for what requestMidi gives, and out. for an output from midi.output().

Interaction: keys and the mouse

A script can be played from the computer keyboard and the mouse. keyPress and keyRelease call a function when a key goes down or comes up, and mouseMovement calls one as the pointer moves, with its place on the page as two numbers from 0 to 1. Cracked had the first and the last as key_press and mouse_movement; those names work here too. 

__().sampler({ id: 'kick', buffer: 'kick' }).to('main');
__().saw({ id: 'lead', gate: 'closed' })
  .lowpass({ id: 'filter', frequency: 800, q: 8 })
  .gain(0.2)
  .to('main');

// Click outside the editor first: keys typed into the editor are left alone.
// Space plays the kick, and A S D F G hold notes for as long as they are down.
const notes = { a: 220, s: 247, d: 277, f: 330, g: 370 };
keyPress(({ key }) => {
  if (key === ' ') __('#kick').trigger();
  if (notes[key]) __('#lead').set({ frequency: notes[key] }).trigger();
});
keyRelease(({ key }) => {
  if (notes[key]) __('#lead').release();
});

// Left to right opens the filter. Towards the top makes it ring.
mouseMovement(({ x, y }) => {
  __('#filter').set({ frequency: 200 + x * 5000, q: 1 + (1 - y) * 15 });
});

Three things differ from Cracked. The callback is given an object with the useful parts picked out (key, code, x, y) and the browser's own event as event. Each helper returns a function that stops it. And keys typed into a text box or the editor do not call back, so that typing code does not play the code being typed.

In the live demo, each run of the code replaces the listeners of the run before, so re-running does not pile them up. In an app of your own, createInteraction() from cracked-up/util gives the three helpers and a clear() that removes everything added through it; make one for each run of a script and clear the one before. Pass an element to listen to just that element, with x and y measured across it. These helpers listen to the page, so a sandboxed script cannot use them: the sandbox has no page of its own. 

import { createInteraction } from 'cracked-up/util';

let interaction = null;
function run(code) {
  const next = createInteraction();
  const program = new Function('__', ...Object.keys(next.helpers), code);
  program(__, ...Object.values(next.helpers));
  interaction?.clear();
  interaction = next;
}

Bypassing a node

A bypassed effect passes its input straight to its output. A bypassed source, or a modulator, is silent. The node keeps running while bypassed, so a delay keeps its contents and an oscillator keeps its phase. The switch is a 5 millisecond crossfade, so it does not click. 

__().saw(110).lowpass({ id: 'filter', frequency: 300, q: 8 }).gain(0.2).to('main');

// Take the filter out on every second beat.
__.transport.sequence('toggle', { steps: [0, 1], step: '1/4' }, (ev) => {
  __('#filter').bypass(ev.value === 1);
});

.bypass() turns the bypass on, .bypass(false) turns it off, and { bypass: true } among a node's options makes it bypassed from the start.

Re-running code: build

A scope's build runs a function that makes nodes, connections and sequences, and then makes the scope match what the function asked for. Run it again with changed code and only the difference is applied:

  • A node that is asked for again is kept and keeps sounding. Changed parameter values are set on it in place.
  • A node is recognised by its id. A node without one is recognised by its position among the nodes of its type: the second lowpass your code makes is the second lowpass it made last time. Give a node an id if you want it to survive being moved around.
  • A node is replaced only if its type or one of its creation options (a sampler's buffer, an oscillator's gate) changed.
  • Nodes, connections and sequences the function no longer asks for are removed.
  • A sequence with a name is replaced in place and stays in time. Give sequences names.
  • If the function throws, everything it did is undone and the scope plays on as it was. 
const scope = engine.scope('track-1');

await scope.build((__) => {
  __().saw({ id: 'bass' }).lowpass(500).gain(0.25).to('main');
});

// Later: the saw and the gain are untouched, the filter moves to 900 Hz, a delay is added.
const result = await scope.build((__) => {
  __().saw({ id: 'bass' }).lowpass(900).delay(0.25).gain(0.25).to('main');
});
result.added;     // [delay]
result.updated;   // [lowpass, gain]  (the gain's input changed)
result.unchanged; // [saw]

The live demo runs your code through build on every key up. A rebuild sets every parameter back to what the code says, so a value changed from a sequence callback lasts until the next rebuild.

scope.apply(graph) does the same from data instead of code: scope.describe() returns a scope's nodes and connections as plain JSON, and apply makes a scope match such a description. That is how a host saves and restores a graph, or edits one from a user interface.

Inspecting the graph

cracked-up/inspect draws a scope as a graph, for finding out why something is silent or where a level goes wrong. Every node is a box, every bus a rounded shape, and signal runs from left to right. Each output has a level meter, and a connection moves only while signal is going through it, so a silent path looks still. It is for a page's own code, not for the live demo; the inspector page shows it running. 

import { toggleInspector } from 'cracked-up/inspect';

// A sidebar with a close button. The same call closes it again.
button.addEventListener('click', () => toggleInspector(engine, { mode: 'sidebar' }));

openInspector(target, { mode }) is the same without the toggling, and mode: 'modal' opens a window over the page. For a layout of your own, such as a panel or a popup window, createInspector draws into an element you give it: 

import { createInspector } from 'cracked-up/inspect';

const inspector = createInspector(engine, { parent: document.querySelector('#graph') });

inspector.setScope(engine.scope('drums'));     // show one scope
inspector.select(engine.select('#filter').first());  // open a node's details
inspector.fit();                               // bring the whole graph into view
inspector.destroy();                           // remove it, and everything it attached

Give it an engine and it shows everything, with each child scope opened as a frame inside the root. Give it a scope and it shows only that scope.

What is drawn

You see It means
A box with a type and an id A node. Classes follow the id. An id the library made up, such as gain-0, is left out. The stripe on the left is coloured for sources and for modulators
A rounded shape A bus. With a dashed outline it belongs to an outer scope and is shown because something here sends to it
A box with a second outline and a small arrow A macro. The arrow opens it in place, as a frame round the nodes inside it. A double click shows only its inside, and the trail at the top leads back out
A hatched box marked "bypassed" A bypassed node

Drag to pan. Pinch, or scroll with Ctrl or Cmd held, to zoom. The view starts at the left of the graph at a size where the labels can be read; Fit shows all of it. Tab reaches every node, Enter opens it, and Escape closes the details and then the window.

Meters

The meter on a node shows the level at its output from -60 dB to full scale: the solid part is the RMS level, the lighter part the peak, and the mark is the highest peak of the last second, which turns red once a peak has gone over full scale. All channels are mixed to one for the reading, so a sound panned hard to one side reads 6 dB low.

Modulators, and everything else whose output only ends up in parameters, are not sound, and decibels say little about them: a 2 Hz wave would read as a level that pumps twice a second. Their meter has zero in the middle and shows the range the value has covered in the last two seconds and where it is now. A connection from one of them moves while the value is changing and stays still while it is steady.

Levels are read by connecting an AnalyserNode to an output. The analyser leads nowhere, so it adds nothing to what you hear and delays nothing; a test renders the same graph with an analyser on every output and without, and the two renders are the same sample for sample. Only outputs that are on screen are listened to, only while audio is running, and destroy() removes them all. In headless Chromium on a laptop the inspector's script took 0.3 ms per frame with 20 nodes in view and 0.85 ms with 100, at a steady 60 frames a second.

A node's details

Clicking a node opens a panel with its description and parameters from the reference, their current values, what is connected to it, a larger meter, a waveform and a spectrum of its output. For a modulator the panel shows the value over the last four seconds instead. There is a bypass switch, and a Trigger button on nodes that can be triggered, except recorders and loopers, where a trigger would record.

Values shown are the ones that were set. A ramp in flight, an offset, or modulation does not show in the number. A modulated parameter names what moves it and the range that signal is covering.

While the graph changes

The inspector follows the scope. It hears about nodes that come and go, and reads the graph again a few times a second for changes that send no event, such as a new connection or a bypass. After a build, nodes that were kept stay where they are and new ones are fitted into the gaps; the pan, the zoom and whatever was opened are left alone. Tidy lays everything out afresh. It works on a suspended context, with the meters idle, and on an offline engine, where it draws the graph and listens to nothing.

Running scripts in a sandbox

Code from someone else should not run in your page, where it could read the page, its storage and the signed-in session. cracked-up/remote lets the same code run somewhere it can do no harm, such as a frame with sandbox="allow-scripts", while the engine stays in the page.

Inside the sandbox, createRemote gives the script the same __. It has no audio behind it: reads are answered from a copy of the scope's state, and everything the script does is sent to the page as plain-data commands. In the page, linkRemote applies those commands to one scope and nothing else. Sequence callbacks run in the sandbox: the page sends each step a little ahead of time, and the commands the callback makes land exactly on the step. 

// In the page
import { linkRemote } from 'cracked-up/remote';

const link = linkRemote(engine.scope('guest'), {
  send: (message) => frame.contentWindow.postMessage(message, '*'),
  allow: (command) => command.op !== 'loadBuffer',   // refuse what you do not want
});
frame.contentWindow.postMessage({ init: link.state() }, '*');
window.addEventListener('message', (event) => {
  if (event.source === frame.contentWindow) link.receive(event.data);
});

// In the sandboxed frame
import { createRemote } from 'cracked-up/remote';

const remote = createRemote({ ...state, send: (message) => parent.postMessage(message, '*') });
window.addEventListener('message', (event) => remote.receive(event.data));

remote.build((__) => {
  __().sampler({ id: 'kick', buffer: 'kick' }).to('main');
  __.transport.sequence('kick', { steps: 'x...' }, (ev) => {
    if (ev.value) __('#kick').trigger();
  });
});

What differs from running next to the engine:

  • Outside a sequence callback there is no clock, so an operation without a time happens when it reaches the page.
  • A script can send audio to an outer bus such as main, but cannot change that bus, and cannot select or change nodes outside its scope.
  • Nodes inside a macro can be written to (__('polysynth lowpass').set(...)) but not read: the sandbox's copy does not include them.
  • There is no transport position to read, and a script cannot start or stop the transport. Sequence events carry the beat and bar.

A script can define its own node types with remote.define, which takes the same definition as defineMacro. The inner graph is built in the sandbox and sent to the page as data. The macro's trigger, release and methods stay in the sandbox and run there whenever anyone calls them, including a control in the page. One difference: a drive's scale has to be data, because a function cannot be sent to the page. 

remote.define({
  type: 'supersaw',
  params: {
    frequency: {
      default: 110, min: 20, max: 5000,
      drives: [
        { select: '#a', param: 'frequency' },
        { select: '#b', param: 'frequency', scale: { multiply: 1.01 } },
      ],
    },
  },
  build(__) {
    __().lowpass({ id: 'filter' }).to('out');
    __().saw({ id: 'a' }).connect('#filter');
    __().saw({ id: 'b' }).connect('#filter');
  },
  methods: {
    sweep(__, args, at) {
      __('#filter').ramp('frequency', args.to, { at, duration: 0.5, curve: 'exp' });
    },
  },
});

remote.buffers.get(key) gives a loaded buffer's duration and slice boundaries, and remote.buffers.load(url) asks the page to load one, which the page may refuse.

The frame keeps a script away from your page, not from the network or the processor. Give the frame a content security policy to stop it making requests, and expect that a script stuck in a loop stops its own sequences. The sandboxed demo shows all of this running, with the measured round-trip time. The guide Running other people's scripts covers when an app needs this, how to set it up safely, and what to share between collaborators.

The editor

cracked-up/editor is a code editor for cracked-up scripts, for an app to embed. It is the editor in the live demo. It completes node types, parameters, selectors, buffer and bus names and helpers as you type, shows what each is when you hover, and shows the source of a node type or helper when you Cmd-click it (Ctrl-click outside macOS), or press F12 on it.

It is built on CodeMirror 6, which is not bundled with the library and not installed with it. The other entry points do not import it. An app that uses the editor installs the CodeMirror packages itself: 

npm install @codemirror/state @codemirror/view @codemirror/commands @codemirror/language \
  @codemirror/autocomplete @codemirror/lang-javascript @lezer/highlight @lezer/common

The editor is plain DOM: give it an element and it fills it. It keeps nothing global, so a page can hold any number of them, and destroy() removes everything one added. A minimal host: 

import { createEngine } from 'cracked-up';
import { helpers, wrapUserCode } from 'cracked-up/util';
import { createEditor, catalogFromEngine } from 'cracked-up/editor';

const engine = await createEngine({ context: new AudioContext() });
const scope = engine.scope('script');

const editor = createEditor({
  parent: document.querySelector('#code'),
  doc: "__().sine(220).gain(0.2).to('main');",
  catalog: catalogFromEngine(engine),
  // Cmd-Enter runs the script. onChange is there too, for running on every edit.
  keymap: [{ key: 'Mod-Enter', run: () => (run(), true) }],
});

async function run() {
  try {
    const program = new Function('__', ...Object.keys(helpers), wrapUserCode(editor.value));
    const result = await scope.build((__) => program(__, ...Object.values(helpers)));
    editor.showError(result.errors[0] ?? null);
  } catch (error) {
    editor.showError(error);
  }
}

The catalog

The editor needs no engine. Everything it knows comes from a catalog, which is plain data: the node types (as engine.registry.list() gives them), the helpers, the buffers with their slice counts, and names that exist outside the document, such as the ids, classes, buses and sequences of another track's script. It adds what it finds in its own document: every id and class, every bus('name') and named sequence, and node types the script defines itself. 

editor.setCatalog({
  types: engine.registry.list(),
  buffers: [{ key: 'kick' }, { key: 'break', slices: 128 }],
  ids: ['lead', 'pad'],          // nodes other scripts made
  classes: ['drums'],
  buses: ['reverb-send'],
  sequences: ['intro'],
  globals: [
    { name: 'engine', description: 'The engine.' },
    // kind says what a name is, so its members are completed: midi.follow(), midi.output().note()
    { name: 'midi', kind: 'midi', description: 'MIDI in and out.' },
  ],
  midiInputs: midi.inputs.map((port) => port.name),    // offered where a port is named
  midiOutputs: midi.outputs.map((port) => port.name),
  // helpers: left out, the library's own are used. To offer keyPress and mouseMovement as well:
  // helpers: [...builtinHelpers(), ...INTERACTION_DOCS]
});

The catalog changes while people type: samples load, macros get defined. Call setCatalog again whenever it does. When several editors show scripts of one project, give them all one store and change that: 

import { createCatalogStore, catalogFromEngine } from 'cracked-up/editor';

const catalog = createCatalogStore(catalogFromEngine(engine));
const drums = createEditor({ parent: drumsElement, doc: drumsCode, catalog });
const bass = createEditor({ parent: bassElement, doc: bassCode, catalog });

engine.buffers.on('ready', () => catalog.set(catalogFromEngine(engine)));
catalog.update({ ids: idsOfEveryTrack() });   // both editors follow

With sandboxed scripts

When scripts run in a sandbox, the editor still lives in the page, and it behaves the same, because it only ever reads the catalog. catalogFromRemoteState makes one from what the link tells the sandbox, which includes node types that a script defined in the sandbox: 

import { catalogFromRemoteState } from 'cracked-up/editor';

editor.setCatalog(catalogFromRemoteState(link.state()));

A page with no engine at all, such as a collaborator's read-only view, can be sent the same data and build its catalog from that.

setReadOnly(true) Stops the user editing. setValue still works.
showError(error, place?) Shows a message under the code and marks a line. The line comes from { line } or { pos } if you give one, from the nodeId of an engine error (the line that gives that id), or for a SyntaxError from the first place the editor's own parser could not read. showError(null) clears it. With errorPanel: false only the line is marked.
focus(), destroy() As named.

Other options: readOnly, lineNumbers, lineWrapping, ariaLabel, keymap (key bindings tried before the editor's own) and extensions (any CodeMirror extensions). editor.view is the CodeMirror view, for anything not covered here. Tab indents; press Escape and then Tab to move focus out of the editor with the keyboard.

Go to definition and the source panel

Cmd-click or F12 on a node type or a helper asks the editor for its definition. A type the script defines itself (define({ type: 'blip', ... })) is in the document, so the cursor goes there. For anything else a panel opens with its description, its parameters, and its TypeScript source with line numbers and a link to the file. A wrapper round a Web Audio node links to that node's page on MDN. A node type's name inside the source is a link to that type, and there is a back button. A type that came only as catalog data, such as one somebody else defined, shows what is known and says the source is not available.

The source of the built-in types and helpers is copied out of the library when it is built, into a file of its own that is loaded the first time the panel opens.

By default the panel is docked at the right of the editor. To put it somewhere of your own, pass an element, or make the panel yourself and share it between editors: 

import { createEditor, createSourcePanel } from 'cracked-up/editor';

const panel = createSourcePanel({ parent: document.querySelector('#sidebar'), catalog });
const editor = createEditor({ parent, catalog, sourcePanel: panel });

panel.show({ kind: 'type', name: 'tapedelay' });   // from a menu of your own, say

To draw the result yourself, take it from onDefinition. It is called first, with the kind, the name, the catalog's data for it, and for a type defined in the script where. Return true and the editor does nothing more: 

createEditor({
  parent,
  catalog,
  sourcePanel: false,
  onDefinition(target) {
    openMyInspector(target.kind, target.name, target.type ?? target.helper);
    return true;
  },
});

builtinSources(kind, name) gives the same source text the panel shows, and the sources option replaces where it comes from.

Styles and themes

The editor brings its styles with it and does not need this site's stylesheet. It adds one <style> element to the document, or to the shadow root it is in; pass injectStyles: false and use the exported editorStyles text if your page must supply it another way. theme is 'auto' (follow the system, the default), 'light' or 'dark', and setTheme changes it. Every colour and font is a CSS custom property that you can set on the editor's element or anything above it: 

.my-app {
  --cu-bg: #101418;
  --cu-text: #e6e6e6;
  --cu-accent: #7fd3a0;
  --cu-font-mono: 'JetBrains Mono', monospace;
  --cu-font-size: 14px;
}

The names are --cu-bg, --cu-text, --cu-muted, --cu-border, --cu-accent, --cu-panel-bg, --cu-hover-bg, --cu-selection, --cu-active-line, --cu-error-bg, --cu-error-text, --cu-shadow, --cu-code-comment, --cu-code-string, --cu-code-number, --cu-code-keyword, --cu-code-dunder, --cu-code-property, --cu-font-mono, --cu-font-ui, --cu-font-size and --cu-line-height. They are also exported as THEME_PROPERTIES.

Sizes, measured on the built files: the editor's own code is 112 kB unminified (29 kB gzipped), and the source text is a separate 121 kB file (about 27 kB gzipped) loaded on first use. Helpers

Helpers are small functions for composing: rhythms, scales, random choices and number conversions. They make no sound themselves. They give you numbers and lists to use in your patterns and parameters. In the live demo and the sandboxed demo you call them by name. In your own project, import them from cracked-up/util (or from cracked-up/global, next to __). 

__.transport.bpm = 100;
__().triangle({ id: 'lead', gate: 'closed' }).lowpass(2400).gain(0.25).to('main');
__().sampler({ id: 'hat', buffer: 'hat' }).gain(0.3).to('main');

// A seed fixes the random choices: the same tune every time. Try another number.
const random = createRandom(4);

// A minor as MIDI notes: 57 is the A below middle C.
const notes = scales('minor').map((step) => 57 + step);
// Decide the tune once: eight notes picked from the scale.
const tune = fillArray(8, () => pick(notes, random));

// Five notes spread evenly over eight steps.
__.transport.sequence('lead', { steps: euclid(5, 8), step: '1/8' }, (ev) => {
  if (!ev.value) return;
  // One time in five, play the note an octave higher.
  const note = tune[ev.index] + (chance(0.2, random) ? 12 : 0);
  __('#lead').set({ frequency: pitchToFreq(note) }).trigger({ duration: ev.duration * 0.8 });
});

// A hat on every third sixteenth note, drifting against the tune.
const third = everyNth(3);
__.transport.sequence('hat', { steps: 'x', step: '1/16' }, () => {
  if (third()) __('#hat').trigger();
});

Random choices that repeat

Every helper that makes a random choice takes an optional last argument: where to get its random numbers. Leave it out and the choice is different on every run. Pass a seeded source and the choices come out the same every time, which is what you want when a piece should sound the same tomorrow, or when you render it to a file. createRandom(seed) makes one, and every engine has one of its own as engine.random. 

__().sine({ id: 'bell', gate: 'closed' }).gain(0.2).to('main');

// A random note of C minor on every eighth note, from the engine's own source.
__.transport.every('1/8', () => {
  const frequency = randomScale('minor', 5, 6, engine.random);
  __('#bell').set({ frequency }).trigger({ duration: 0.1 });
});

Every helper

The results shown are what the example gives. Where a helper has a second name, that is the name Cracked used for it, and it works here too.

Three things differ from Cracked on purpose. chance takes a probability from 0 to 1, not a percentage. shuffle returns a new list and leaves yours alone. pitchToFreq and freqToPitch do not round, so notes between the keys work.

euclid's third argument, rotate, starts the pattern that many steps later, which moves the hits earlier: euclid(3, 8) is [1, 0, 0, 1, 0, 0, 1, 0] and euclid(3, 8, 1) is [0, 0, 1, 0, 0, 1, 0, 1]. A negative number moves them later.
